# SOAP 1.1 на границе JMS

SOAP 1.1 используется по умолчанию для всех JMS-очередей. Очереди с обычным XML перечисляются в исключениях.
`MessageProcessor`, `EnrichingMessageProcessor` и
`JmsEnrichmentOperation` работают с XML-документом из Body: SOAP-конверт им не передаётся, формировать его не нужно.
JAXB и проверка бизнес-документа по XSD остаются в `XmlService` и обработчиках.

## Конфигурация

```yaml
runtime-lite:
  listeners:
    max-body-bytes: 10485760
  soap:
    plain-jms-destinations:
      - SAMPLE.XML.INPUT
      - SAMPLE.XML.OUTPUT
    max-depth: 128
    max-elements: 100000
```

Имена очередей в примере синтетические. Для входа очередь берётся из настройки маршрута; для внешнего запроса и
ответа — из настройки операции обогащения; для результата — из назначения `OutboundMessage`.

Пустой список `plain-jms-destinations` означает SOAP 1.1 для всех JMS-очередей. Для очередей из списка упаковка и
распаковка отключаются: передаётся обычный XML/текст. Сравниваются точные имена очередей, шаблоны не применяются.
Kafka не использует этот список, даже если имя topic совпадает с именем очереди. Автоматического распознавания
версии и режима по телу нет: вход в очередь без исключения должен содержать SOAP 1.1 Envelope.

Прежний параметр `jms-destinations` удалён. Если он остался в настройках, приложение завершает запуск с ошибкой
конфигурации. При переходе перечислите в `plain-jms-destinations` именно очереди, которым требуется обмен без SOAP.

Лимит `max-body-bytes` применяется к полному SOAP-сообщению в UTF-8, включая Envelope. Ограничения глубины и числа
элементов тоже учитывают конверт. Их увеличение увеличивает допустимые затраты памяти: SAAJ строит DOM.

- `max-depth: 128` — максимальное число вложенных XML-элементов на одном пути. Envelope имеет глубину 1, Body — 2,
  корень бизнес-документа — 3. У пути `Envelope/Body/Item/name` глубина 4.
- `max-elements: 100000` — максимальное общее число XML-элементов в сообщении, включая SOAP Header при наличии.
  Каждый элемент считается один раз; атрибуты, текст и закрывающие теги отдельно не считаются.

При превышении любого ограничения SOAP-сообщение отклоняется. Эти ограничения применяются при упаковке и распаковке;
для очередей из списка исключений сохраняются ограничения обычного XML-слоя и общий лимит входного JMS-сообщения.

## Обработка и хранение

`SoapService` использует Jakarta SOAP API и Eclipse Metro SAAJ. Он принимает SOAP 1.1 с одним XML-элементом в Body.
На входе инфраструктура сохраняет полный конверт, снимает оболочку и вызывает обработчик с отдельным XML-документом.
Наследуемые объявления пространств имён переносятся к корню извлечённого документа, включая объявления для
QName-значений. Префиксы и сериализация внутреннего документа могут отличаться от исходной строки.

Исходящий XML оборачивается в `MessagePublisher` до записи в outbox. В outbox сохраняется готовое тело, поэтому
повторная отправка через `BrokerMessageSender` не добавляет второй конверт и не пересоздаёт SOAP. Сохраняются
прикладные JMS-свойства, ключ и действующие правила `JMSCorrelationID`/`JMSReplyTo`.

SOAP-конверты сохраняются в существующих текстовых колонках inbox, outbox и принятого ответа. Это сохраняет исходную
строку конверта при чтении через JDBC без преобразований типа PostgreSQL XML. Обычные сообщения сохраняют прежний
выбор XML/текстового формата. `TextMessage` передаёт строку; побайтовый аудит исходной сетевой передачи не выполняется.

Для асинхронного обогащения `validateReply()` получает извлечённый XML и возвращает тот же XML с выбранным форматом
хранения. Приёмник проверяет совпадение именно с извлечённым телом, а в БД сохраняет полный исходный SOAP-ответ.
После восстановления `decode()` и `map()` снова получают только внутренние документы. Причины сбоя и пропуск
внешнего вызова также передаются в `map()` вместе с обычным XML исходного сообщения.

Миграция `jms-payload-format` добавляет формат принятого документа и ожидаемый формат ответа к сохранённому состоянию.
Формат ответа фиксируется при создании запроса. Поэтому изменение списка исключений после перезапуска не меняет
декодирование уже принятых документов и ожидаемых ответов. Старые записи получают `PLAIN`. Формат нового исходящего
результата определяется настройками на момент его создания; уже сохранённый outbox доставляется без изменений.

## Ошибки и ограничения

- Поддерживается document/literal: один бизнес-элемент либо SOAP 1.1 Fault. SOAP 1.2, вложенный Envelope и SOAP encoding
  отклоняются. WSDL operation wrapper при наличии является частью XML в Body и должен соответствовать бизнес-модели.
- Необязательные SOAP Headers принимаются и не передаются дальше. Неизвестный `mustUnderstand="1"`, адресованный
  конечному получателю или actor `next`, отклоняется. Исходящие конверты не содержат SOAP Header; копирования входных
  заголовков нет. Обязательные прикладные SOAP Headers требуют отдельного согласованного расширения.
- SOAP Fault определяется до вызова операции и преобразуется в `INVALID_REPLY` в сценарии обогащения.
  Автоматического повторного бизнес-запроса или трактовки технического Fault как бизнес-отказа нет.
- Неправильный SOAP-ответ также даёт `INVALID_REPLY`. Ошибка SOAP на обычном входе откатывает обработку и передаётся
  стандартному механизму JMS redelivery; предел повторов и DLQ определяются настройками брокера.
- Ошибка формирования итогового SOAP в асинхронном `map()` даёт терминальный `MAPPING_FAILED`; при уже имеющейся
  причине сбоя сохраняется она. Ошибка БД откатывает транзакцию и допускает повтор. Ошибки SOAP до записи outbox
  специально не помечают участвующую транзакцию как rollback-only, чтобы воркер мог сохранить терминальный исход.
- DTD, внешние ресурсы и processing instructions запрещены. В логи и сообщения исключений не выводится тело XML.
- Принятый корректный ответ хранится до завершения workflow и затем очищается по существующим правилам.
  Некорректные ответы и Fault отдельным аудитом не сохраняются.

Стандартный W3C SOAP over JMS binding, WS-Security, подпись/шифрование, вложения/MTOM и генерация SOAP-сервисов по WSDL
в этот слой не входят. Для них требуется отдельный контракт и выбор подходящего SOAP-стека.

## Проверка

Модуль собирается на JDK 21:

```bash
mvn -B -f runtime-lite/pom.xml verify
```

Интеграционные проверки используют профиль `int-test` с выделенными PostgreSQL и Artemis. Подключения задаются
`IIB_LITE_INT_POSTGRES_URL`, `IIB_LITE_INT_POSTGRES_USER`, `IIB_LITE_INT_POSTGRES_PASSWORD`,
`IIB_LITE_INT_ARTEMIS_URL`, `IIB_LITE_INT_ARTEMIS_USER`, `IIB_LITE_INT_ARTEMIS_PASSWORD`.

```bash
mvn -B -f runtime-lite/pom.xml -Pint-test verify
```

Тестовые сообщения и имена ресурсов синтетические. SOAP-проверки покрывают пространства имён, Fault, ограничения,
запрет DTD и processing instructions, формат после восстановления и отсутствие конверта во всех бизнес-обработчиках.
