# Функциональные требования к проекту iib-camel

> 🇬🇧 English version: [functional-requirements.en.md](functional-requirements.en.md)

Инструмент миграции приложений с IBM Integration Bus (IIB/ACE) на Spring Boot + Apache Camel.

Уточнение от 2026-10-23: самостоятельный runtime для ручной миграции определяется разделом 7. Требования к исполнению сгенерированных маршрутов ниже сохраняются для legacy compatibility-среды конвертера и не задают архитектуру нового runtime.

Каждое требование размечено приоритетом по методике **MoSCoW** (см. раздел 5):
**Must** — обязательно для первой версии, **Should** — важно, допускается отложить, **Could** —
желательно, делается при наличии ресурсов, **Won't** — осознанно не делается в этой версии.

## 1. Термины и сокращения

| Термин | Определение |
|--------|-------------|
| **IIB** | IBM Integration Bus / IBM App Connect Enterprise (ACE) — интеграционная платформа |
| **msgflow** | Файл описания потока сообщений (`.msgflow`) |
| **subflow** | Файл описания подпотока (`.subflow`) |
| **ESQL** | Extended SQL — процедурный язык IIB для узлов Compute, Filter, Database |
| **Message Set** | Набор описаний форматов сообщений (`.mset`, XSD, DFDL, JSON-схемы) |
| **ULM** | Унифицированная логическая модель (Unified Logical Message) IIB: Properties, MQMD, Body, Environment, LocalEnvironment, DestinationList |
| **Промежуточная модель (IR)** | Внутреннее представление артефактов после парсинга, на котором строятся все генераторы |
| **Конвертер** | Отдельное one-shot Java-приложение (модуль `converter`), выполняющее конвертацию IIB-артефактов в целевые артефакты |
| **Runtime-сервис** | Самостоятельное Spring Boot приложение `runtime` для вручную реализованных модулей; прежний исполнитель generated-маршрутов сохранён в `compatibility-tests/legacy-runtime` |

## 2. Состав продукта и контекст использования

Продукт состоит из двух компонент:

1. **Конвертер** (one-shot CLI, модуль `converter`) — запускается по команде, разбирает артефакты IIB,
   генерирует Camel XML DSL, Java-классы, MapStruct-мапперы и отчёт о миграции, после чего завершается.
   Не оставляет фоновых процессов и не поднимает веб-служб.
2. **Runtime-сервис** (модуль `runtime`, Spring Boot) — исполняет подготовленные маршруты Camel:
   это сервис, на котором мигрированная интеграция реально работает.

Система применяется:

- инженерами-интеграционщиками при миграционных проектах «IIB → Spring Boot + Apache Camel»;
- в CI/CD: конвертер регенерирует целевые артефакты после изменения исходных потоков;
- как одношаговый конвертер при первичном переносе и как генератор заготовок при итеративном переносе.

**Система не является** рантайм-средой для IIB и не заменяет ручной анализ бизнес-логики.

### 2.1. Уточнение целевого профиля — 2026-10-23

Эта область поставки определяет приоритеты текущего этапа; широкий каталог ниже описывает также дальнейшие возможности и не требует реализовать все адаптеры IIB.

- **FR-P1.1. (Must)** Основные транспорты целевых сценариев — MQ и Kafka. REST и SOAP добавляются по потребности конкретных примеров. MQ/JMS на Artemis уже проверен; Kafka пока является требованием к дальнейшей реализации.
- **FR-P1.2. (Must)** Сохранить доступ к существующей БД и получение данных из справочников, используемых ESQL-преобразованием. Основной механизм — Spring JDBC; JPA/Hibernate допускается при обоснованной необходимости модели сущностей и её жизненного цикла. Наличие большого XML-маппинга само по себе не требует JPA. Поддержка всех Database-узлов IIB из этого требования не следует.
- **FR-P1.3. (Must)** Функциональное поведение определяется контрактом мигрируемого сценария: сохраняются условия и порядок отправок, используемые свойства/кодировки сообщений и пути ошибок. MQRFH2, Encoding/CCSID, дополнительные терминалы, promoted properties и обращения к БД должны иметь явное правило миграции либо диагностику неподдерживаемости. Точное отображение заголовков в целевой протокол и границы транзакций проверяются отдельно; смена брокера сама по себе их не определяет.

Поддержка каждой возможности подтверждается отдельными синтетическими сценариями и проверкой поведения. Конфиденциальные исходники и результаты их предметного разбора хранятся отдельно от публикуемой документации.

## 3. Функциональные требования: конвертер

### 3.1. Входные данные: приём и разбор артефактов IIB

- **FR-1.1. (Must)** Система должна принимать на вход каталог проекта IIB (или его часть) и разбирать файлы типов:
  - `.msgflow` — потоки сообщений;
  - `.subflow` — подпотоки;
  - `.esql` — модули ESQL;
  - `.mset`, `.mxsd`, XSD, DFDL и JSON-схемы — наборы сообщений и модели данных;
  - файлы проекта (`.project`, `MANIFEST.mf` — деплой-манифесты библиотек и приложений).
- **FR-1.2. (Must)** Система должна поддерживать пакетную обработку: конвертацию всех артефактов
  указанного каталога за один запуск.
- **FR-1.3. (Must)** При разборе система должна валидировать структуру файлов и сообщать об ошибках разбора
  с указанием файла, строки/позиции и причины.
- **FR-1.4. (Must)** Система должна строить промежуточную модель (IR), содержащую:
  - топологию потоков: узлы, типы узлов, терминалы (in/out/catch/fail и др.), соединения;
  - свойства узлов (конфигурации, фильтры, выражения ESQL);
  - связи потоков с подпотоками и модулями ESQL;
  - схемы сообщений, привязанные к узлам указанием формата.
- **FR-1.5. (Must)** Система должна разрешать ссылки между артефактами: подпотоки внутри потоков,
  ESQL-модули на узлах Compute/Filter/Database, схемы на входных/выходных узлах. Неразрешённые ссылки
  фиксируются как предупреждения в отчёте.

### 3.2. Генерация Apache Camel (XML DSL)

- **FR-2.1. (Must)** Система должна генерировать маршруты Apache Camel в формате XML DSL (`<routes>…</routes>`)
  на основе потоков `.msgflow`.
- **FR-2.2. (Must/Should)** Система должна сопоставлять узлы IIB элементам Camel в соответствии с таблицей
  соответствия. Базовый набор узлов (ввод/вывод, Router, Filter, Throw, Validate, обработка catch/fail) —
  **Must**; расширенный набор (Aggregate, Resequence, TimeoutControl, Database и др.) — **Should**;
  точные правила — предмет настройки конфигурацией:

  | Узел IIB | Целевой элемент Apache Camel |
  |----------|------------------------------|
  | MQInput / HTTPInput / FileInput / JMSInput | from: `jms`, `netty-http` / `platform-http`, `file`, `camel-jms` и др. |
  | MQOutput / HTTPReply / FileOutput / JMSReply | to (синхронные/асинхронные варианты) |
  | Router (Route) / Filter | `choice`/`when`/`otherwise`, `filter` |
  | Compute (ESQL) | процессор/бину-обёртка; см. FR-3.x |
  | Mapping | генерация маппера MapStruct и вставка вызова; см. FR-4.x |
  | TryCatch | `doTry`/`doCatch` |
  | Throw | `throwException` |
  | Validate | `validate` (XSD/JSON) |
  | Trace | ведение журнала (`log`, `wireTap` на охраняемый канал) |
  | Loop / While | `loop`, `while` |
  | Aggregate / Collect | `aggregate` с кастомной стратегией агрегации |
  | Resequence | `resequence` |
  | Split | `split` |
  | TimeoutControl / TimeoutNotify | `aggregate` + таймер/`scheduler` |
  | SFTP/FTP (File*) | `sftp`/`ftp` |
  | Database (SQL) | `sql`/`jdbc` |
  | SetVariable / ResetContentDescriptor | установка свойств обмена (`exchangeProperty`, `setHeader`) |
  | Request-поддерево (пары Request/Reply) | `to` + `setExchangePattern` (`InOut`) |
  | подпоток (`.subflow`) | разворачивание во вложенный шаг маршрута (`direct`/`route`-вставка или выделенный `<route>` с вызовом через `to`) |

  **Покрытие каталога узлов IIB (оценка, 2026-10).** Палитра built-in узлов IIB/ACE 12.x насчитывает
  **~100+ типов узлов** (группируются в ~15 категорий-drawers). Конвертер поддерживает базовые виды
  (`MQInput`, `MQOutput`, `Compute`, `Route` + семантика catch/fail терминалов) и подпотоки
  (`.subflow` → direct-вызов + вложенный маршрут; узлы Input/Output подпотока — терминалы
  `eflow:FCMSource`/`eflow:FCMSink`) — формально ~7% каталога.
  Разбивка по категориям и приоритеты расширения (FR-2.2 Should):

  | Категория IBM | Примеры узлов | Статус | Кандидаты (Should) |
  |---|---|---|---|
  | Construction | Input, Output, Compute, Filter, Route, Throw, TryCatch, Validate | 2 из ~10 (Compute, Route) | Filter |
  | MQ | MQInput, MQOutput, MQReply, MQGet, MQHeader, Publish | 2 из ~7 (MQInput, MQOutput) | MQReply (request/reply), MQGet |
  | JMS | JMSInput/Output/Reply/Receive | 0 из 4 | JMSInput, JMSOutput (почти 1:1 к правилам MQ) |
  | Transformation | ResetContentDescriptor, SetVariable | 0 | ResetContentDescriptor |
  | Trace/Verify | Trace | 0 из 1 | Trace (→ `to(log)`, тривиально) |
  | Timing | TimeoutNotification/Control, Timer | 0 | TimeoutNotification (→ `timer`) |
  | Collating | Collector, Resequence, Sequence | 0 | по потребности |
  | Database | DatabaseInput, DatabaseRetrieve, DatabaseRoute | 0 | вертикаль `sql`/`jdbc` целиком |
  | Web services | HTTPInput/Reply/Request, SOAPInput/Request/Extract, REST* | 0 | отдельная вертикаль транспортов |
  | File/Email | FileInput/Output/Read, EmailOutput | 0 | FileInput, FileOutput |
  | Kafka | Kafka-узлы и их конфигурация | 0 | целевая вертикаль текущего профиля; пока не реализована |
  | Прочее (адаптеры) | CD*, Salesforce, SAP, BigData, IoT и др. | 0 | вне рамок текущего этапа |

  Узлы, не покрытые таблицей соответствия FR-2.2, не отбрасываются: согласно FR-2.7 конвертер
  создаёт TODO-заглушку и помечает узел в отчёте (FR-5.1), так как потеря правил не допускается.
- **FR-2.3. (Must)** Система должна сохранять структуру связей терминалов: ветвления, соединения к различным
  выводам, обработчики catch/fail — отображаются в соответствующие конструкции (`choice`, `doTry`,
  `onException`, `errorHandler`).
- **FR-2.4. (Should)** Для каждого подпотока, входящего в поток, система должна либо построить отдельный
  маршрут (`<route>` с входной точкой через `direct:` по имени подпотока), либо инлайнить его шаги в
  родительский маршрут. Способ выбирается настройкой (по умолчанию — `direct:` маршрут).
- **FR-2.5. (Must)** Сгенерированные XML должны быть валидными и пригодными для загрузки в Camel-контекст
  runtime-сервиса без ручной правки синтаксиса.
- **FR-2.6. (Should)** Каждый сгенерированный маршрут/шаг должен содержать комментарий с указанием
  источника: имя потока, узла, строки исходного файла (трассируемость).
- **FR-2.7. (Should)** Узлы, для которых не определено правило конвертации, не отбрасываются: система
  должна помечать такие узлы в отчёте (FR-5) и генерировать заглушку с TODO-комментарием.

### 3.3. Перевод ESQL

- **FR-3.1. (Should)** Система должна разбирать синтаксис ESQL: модули, функции, процедуры, объявления
  `DECLARE`, выражения `SET`/`IF`/`CASE`/`ELSEIF`, предикаты, циклы (`LOOP`, `WHILE`), обработку
  (`HANDLER`), вызовы (`CALL`), `BROWSE`/`PASSTHRU` (на уровне распознавания и предупреждений).
- **FR-3.2. (Should)** Система должна транслировать:
  - выражения ESQL (арифметические, логические, строковые, функции `CAST`, `SUBSTRING`, `UPPER`, и др.)
    в эквиваленты Java/выражений Camel (`simple`, `ognl`, `xpath`);
  - предикаты фильтров (узлы Filter, Route-условия) в предикаты Camel (`simple`/`jsonpath`/`xpath`);
  - ветвления `IF/ELSE` и `CASE` в конструкции procesоров (`choice`) либо Java-код;
  - обращения к дереву сообщения (`InputRoot`, `OutputRoot`, `Environment`, `LocalEnvironment`,
    `Properties`, `MQMD`) в операции с телом и заголовками обмена Camel или в вызовы промежуточных
    POJO-моделей ULM.
- **FR-3.3. (Should)** Выражения, не поддающиеся автоматической трансляции, должны:
  - либо транслироваться частично с оставлением комментария-заглушки `TODO` и ссылки на исходную строку;
  - либо помечаться в отчёте как требующие ручной разработки.
- **FR-3.4. (Should)** Система должна генерировать промежуточные POJO-классы (модель ULM: тело сообщения,
  заголовки, Environment/LocalEnvironment) для использования в процессорах и мапперах — на основе
  данных анализируемых схем (Message Set) и обнаруженных обращений к дереву в ESQL.
- **FR-3.5. (Should)** Фрагменты ESQL, целиком привязанные к конкретному узлу Compute, должны
  транслироваться в отдельные классы/методы, вызываемые из маршрута (`bean`, `process`), с сохранением
  связи «узел ↔ метод».

  Статус реализации (2026-10-22): первый автоматический уровень перевода работает. Конвертер
  генерирует Spring-бины из Compute-модулей (FR-3.5 в объёме «узел ↔ метод»): `bean id = camelize(модуль)`,
  бин наследует `AbstractComputeBean` (protected `copy`/`mqmd`/`setBodyField`; публичный шлюз
  `compute(Exchange)` с `@Handler`), операторы переносятся с трассируемым оригиналом (`// SET …`).
  Переводимое подмножество FR-3.2: `SET OutputRoot = InputRoot` (pass-through), `SET OutputRoot.MQMD.<F> = '<s>'`
  (JMS-свойство), `SET OutputRoot.<domain>.<Path> = '<s>'` (правка XML-дерева тела), `CAST('<lit>' AS T)`
  (литерал + примечание о типе). Ветвления `IF/WHILE`, `CALL`, `THROW`, функции ≠ Main, FILTER-модули —
  честный статус «частично»: TODO-заглушки в бине с текстом исходного оператора и причины в отчёте
  (FR-3.3); SET внутри ветвлений не переводится безусловным оператором.

  Статус FR-3.4 (2026-10-22): первый уровень — конвертер генерирует POJO-модели тела сообщения
  (`output/models/`, пакет `runtime.generated.model`): класс на корень ESQL-пути, поля String с
  javadoc-ссылками на породившие их операторы. Компромиссы: типы не выводятся (CAST остаётся строкой),
  поведение бина правит тело динамически (не через модель), глубокие пути сплющены. Модели — наглядная
  основа для будущих мапперов FR-4.1; полный ULM-выход (по Message Set) остаётся вне этого уровня.

Уточнение реализации после исправления блокирующих дефектов (2026-10-22): неполные ESQL-бины явно останавливаются до любых бизнес-операций; блоки управления не разбираются на безусловные SET. Route сохраняет XPath и все строки filterTable с режимами First/All. XML-пути включают корень документа; JSON, namespaces и индексы в ESQL-путях пока отклоняются. Это ограниченный профиль, полный ULM и MapStruct остаются задачами следующих итераций. Подробности: [ход реализации](implementation-progress.ru.md).

Обновление B1 (2026-10-22): вложенные однотерминальные подпотоки разрешаются канонически и выдаются один раз на пакет; граф сохраняет fan-out/продолжение MQOutput, циклы и неизвестные терминалы диагностируются. Поддержаны цепочки Input.catch и локальных Compute/Route.failure с восстановлением входного сообщения. MQInput.failure и многократная пропагация подпотоков остаются вне реализованного профиля. Каталог вывода защищён manifest и проверками коллизий/путей.

### 3.4. Генерация MapStruct-мапперов

- **FR-4.1. (Must/Should)** По логике узлов Mapping (потоки преобразования сообщений) система должна
  генерировать Java-интерфейсы и реализации мапперов **MapStruct** (аннотация `@Mapper`). Базовые
  правила — **Must**; сложные схемы — **Should**. Правила включают:
  - маппинг «поле → поле» (Must);
  - преобразования типов (аналог `CAST`) (Should);
  - константные значения и значения по умолчанию (Should);
  - выражения/вычисляемые поля (аналог `user-defined` функции Mapping) (Should);
  - условные маппинги (аналог условий Mapping) (Should);
  - многократные источники/приёмники — агрегация полей из нескольких деревьев (Should).
- **FR-4.2. (Should)** По узлам Compute система должна генерировать мапперы для типовых операций
  «входной объект → выходной объект» (копирование/преобразование структуры Body):
  - простое копирование — через автогенерацию метода маппера (source-target по имени поля/листа);
  - сложные операции — класс Java (`@Mapper` + вспомогательные методы `@Named`)
    с комментариями-ссылками на строки ESQL.
- **FR-4.3. (Must)** Система должна генерировать маркировку мапперов
  (`@Mapper(componentModel = MappingConstants.ComponentModel.SPRING)`),
  чтобы они встраивались в Spring-контекст runtime-сервиса.
- **FR-4.4. (Must)** Сгенерированные мапперы должны компилироваться без ручных правок синтаксиса
  и ссылаться на классы промежуточной модели (FR-3.4).

### 3.5. Отчёт о миграции и трассируемость

- **FR-5.1. (Must)** После обработки система должна формировать отчёт о миграции (формат — минимум
  Markdown, опционально HTML/JSON), содержащий:
  - перечень разобранных входных файлов и артефактов;
  - каждую единицу конвертации (поток, узел, ESQL-оператор) со статусом: *конвертировано* /
    *частично* / *требует ручной доработки* / *не поддерживается*;
  - список проблем разбора (ошибки, предупреждения);
  - статистику по количеству узлов/операторов каждого типа и статусам.
- **FR-5.2. (Should)** Каждая запись отчёта должна содержать ссылку на источник (файл, узел, строка
  ESQL) и, при наличии, на сгенерированный файл/фрагмент.
- **FR-5.3. (Could)** Статистика и статусы должны позволять оценивать полноту миграции проекта
  (например, % сконвертированных узлов).

### 3.6. Валидация сгенерированных артефактов

- **FR-6.1. (Should)** Система должна валидировать сгенерированные Camel XML на синтаксис
  (соответствие XSD Camel Runtime) и наличие всех ссылок (`direct:`-точки, bean-идентификаторы).
- **FR-6.2. (Could)** Валидация сгенерированных Java/MapStruct исходников на компилируемость
  (в т.ч. запуск `mvn compile` в темп-каталоге) — при включённой опции.

### 3.7. Интерфейс пользователя (CLI, API)

- **FR-7.1. (Must)** Система должна предоставлять CLI-команду запуска конвертации со следующими
  параметрами (минимальный набор):
  - входной каталог/файлы;
  - выходной каталог;
  - формат вывода (маршруты, мапперы, модель, отчёт) — по умолчанию все;
  - режим встраивания подпотоков (`direct`/`inline`);
  - файл конфигурации соответствий (таблица FR-2.2) для переопределения правил;
  - уровни логирования.
- **FR-7.2. (Should)** Система должна быть пригодна для встраивания в более крупное приложение
  (публичный Java-API конвертации).
- **FR-7.3. (Could)** Стратегическая задача: веб-интерфейс (редактор правил соответствий, визуализация
  потока ↔ маршрут).

### 3.8. Конфигурируемость и расширяемость

- **FR-8.1. (Should)** Правила соответствия «узел IIB → элемент Camel» должны быть вынесены в
  конфигурацию (внутренний дефолтный набор + внешняя переопределяемая таблица).
- **FR-8.2. (Could)** Должна существовать точка расширения (плагины/интерфейс SPI) для добавления:
  - новых типов входных артефактов;
  - новых правил сопоставления узлов;
  - новых стратегий генерации.

## 4. Функциональные требования: runtime-сервис

Runtime-сервис — приложение на **Spring Boot + Apache Camel** (стек: Java 25, Spring Boot 4.x),
на котором работает вся мигрированная интеграция. Он принимает на вход артефакты, подготовленные
конвертером, и исполняет их.

### 4.1. Состав и модель развертывания

- **FR-R1.1. (Must)** Runtime-сервис реализуется как приложение Spring Boot (Java 25) и является
  единственной рантайм-компонентой продукта: всё после конвертации работает именно на нём.
- **FR-R1.2. (Must)** Конвертер поставляется отдельно как one-shot Java-приложение (CLI): запускается
  по команде, завершается по окончании конвертации, не оставляет фоновых процессов и не поднимает
  веб-служб.
- **FR-R1.3. (Must)** Репозиторий организуется как multi-module Maven: родительский `pom.xml`,
  модуль `converter` (конвертер) и модуль `runtime` (исполняющий сервис). Сборка выполняется одной
  командой Maven из корня.

### 4.2. Загрузка маршрутов Camel

- **FR-R2.1. (Must)** Сервис должен загружать маршруты из XML DSL `<routes>`, расположенных в каталоге
  `camel/` на classpath (`camel/*.xml`) — сгенерированные маршруты поставляются внутри jar сервиса
  (базовая модель развертывания).
- **FR-R2.2. (Should)** Дополнительно должна поддерживаться загрузка маршрутов из внешнего каталога
  (путь задаётся настройкой `camel.springboot.routes-include-pattern`), без изменения кода сервиса —
  для сценария «обновление маршрутов без пересборки jar».
- **FR-R2.3. (Should)** Ошибки разбора маршрутов при старте должны приводить к падению сервиса
  (fail-fast) с диагностикой конкретного файла и строки.
- **FR-R2.4. (Could)** Горячая перезагрузка маршрутов без перезапуска сервиса — вне первой версии.

### 4.3. Бины, модели и мапперы

- **FR-R3.1. (Must)** Все классы, подготовленные конвертером (процессоры для узлов Compute, модели ULM
  из FR-3.4, MapStruct-мапперы), компилируются и поставляются в jar сервиса как Spring-компоненты;
  ссылки на них из XML-маршрутов (`<bean>`, `method=…`) должны разрешаться в Spring-контексте.
- **FR-R3.2. (Should)** Дополнительно должен поддерживаться альтернативный вариант поставки:
  сгенерированные классы как отдельная Maven-зависимость (library), подключаемая к модулю `runtime`.

### 4.4. Подключения (адаптеры)

- **FR-R4.1. (Must)** Основной JMS-провайдер пилота — Apache Artemis через `camel-jms`. Профиль
  `artemis` подключается к внешнему брокеру с постоянным хранилищем; локальный embedded Artemis
  предназначен для разработки и тестов. URL, учётные данные, пул и очереди задаются внешней
  конфигурацией, секреты не хранятся в репозитории. Обязательный сценарий — синхронный InOnly
  queue → Camel/`direct:` → queue в пределах одной `ConnectionFactory` и локальной JMS-транзакции.
- **FR-R4.2. (Should)** IBM MQ — опциональный JMS-провайдер для отдельного профиля и стенда. Настройки
  host, port, queue manager, channel, очередей, пула, аутентификации и TLS задаются конфигурацией.
  Он не блокирует пилот с Artemis; поведение IBM MQ и соответствие JMS application properties полям
  MQMD подтверждаются отдельно на IBM MQ, а не выводятся из теста на Artemis.
- XA-транзакции и exactly-once гарантии вне области текущей версии (см. Won't).

### 4.5. Надёжность и наблюдаемость

- **FR-R5.1. (Must)** Для профиля Artemis единая политика ошибок работает с локальной JMS-транзакцией:
  необработанная ошибка откатывает вход и JMS-отправки текущей попытки; после настроенного числа
  повторов исходное сообщение направляется в DLQ без повторного исполнения бизнес-маршрута. Если
  отправка в DLQ не удалась, транзакция откатывается и карантин повторяется. Получатель и ограниченные
  параметры повторов конфигурируются; сгенерированные маршруты не требуют индивидуального обработчика
  для базового режима. Это ограниченный контракт redelivery, не exactly-once и не гарантия точного
  счётчика доставок после любых сбоев.
- **FR-R5.2. (Should)** Наблюдаемость: Actuator (`/actuator/health`, `/actuator/metrics`), метрики
  Micrometer (в т.ч. счётчики обменов по маршрутам), структурное журналирование с идентификатором
  обмена (correlation id) в каждой строке.
- **FR-R5.3. (Should)** Graceful shutdown: при остановке сервиса текущие обмены завершаются,
  приём новых — прекращается.
- **FR-R5.4. (Could)** Трассировка (OpenTelemetry) сквозь маршруты.

### 4.6. Конфигурация и развертывание

- **FR-R6.1. (Must)** Вся конфигурация (подключения, каталоги маршрутов, профили) — через
  `application.yml` и переменные окружения; секреты не хранятся в репозитории.
- **FR-R6.2. (Should)** Сервис упаковывается исполняемым jar (spring-boot repackage) и запускается
  одной командой; CI/CD-сценарий: конвертер → пересборка runtime → deploy jar.
- **FR-R6.3. (Could)** OCI-образ (Docker) и шаблон развертывания.

## 6. Не делаем в текущей версии (Won't have)

- Полный разбор DFDL-схем;
- Автоматическая генерация интеграционных тестов по исходным потокам;
- XA-транзакции и жёсткие гарантии доставки (переносятся вручную);
- Обработка узлов, требующих рантайма ACE (например, части нестандартных свойств Database-узлов);
- Редактирование исходных потоков/бизнес-логики средствами системы.

## 7. Самостоятельный runtime ручной миграции

- **FR-MR1 (Must)** Runtime собирается и запускается на Java 21 без конвертера, его артефактов и общего Maven parent. Один репозиторий и корневой агрегатор допустимы. Используются стабильный Spring Boot, Camel XML DSL, BOM и Jackson XML.
- **FR-MR2 (Must)** IBM MQ, Artemis и Kafka включаются независимо и могут работать одновременно. Адреса, авторизация, пул и параметры TLS/SASL задаются внешней конфигурацией. Реальная проверка каждого провайдера и его контракта сообщений выполняется отдельно.
- **FR-MR3 (Must)** Один модуль интеграции — один каталог Maven с Java-обработчиками, XML-маршрутами, конфигурацией, тестами и документацией. Подключение модуля требует пересборки приложения; автоматический перенос ESQL и горячая загрузка не требуются.
- **FR-MR4 (Must)** PostgreSQL и Spring JDBC обеспечивают чтение справочников, запись бизнес-данных и inbox/outbox. JPA вводится только при обосновании и после согласования транзакций. Вход, бизнес-записи и неизменяемые выходы со статусом READY фиксируются одной транзакцией БД до ACK/commit offset.
- **FR-MR5 (Must)** Отправитель захватывает готовые записи с поддержкой нескольких экземпляров, ждёт подтверждения брокера и записывает PROCESSED. Нужны повторные попытки, восстановление после падения, ограничения числа попыток и стабильный event ID. Гарантия — как минимум одна доставка с дедупликацией; XA и exactly-once не заявляются. PROCESSED означает принятие брокером.
- **FR-MR6 (Must)** Локальный стенд, пример модуля и инструкции используют только синтетические данные. Конфиденциальные исходники и документация конкретных бизнес-модулей не публикуются. Health/readiness и graceful shutdown входят в каркас; эксплуатационные политики уточняются для каждого модуля.
