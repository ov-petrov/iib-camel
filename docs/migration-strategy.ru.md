# Стратегия переноса IIB/ESQL на Spring Boot

Дата: 23 октября 2026 года. Статус: **архитектурная рекомендация для обсуждения**, не утверждённая смена стека и не отчёт о готовой реализации. Исходный анализ от 22 октября остаётся историческим baseline.

Документ описывает общие подходы. Конфиденциальные исходники, их структура и предметные правила сюда не включены.

## Вывод

Перенос ESQL на Java технически реализуем. Основной объём работы — понять и проверить поведение исходного приложения. Выбор между Camel и Spring Messaging этот объём существенно не устраняет.

Рекомендуемый результат проекта — **инструмент управляемой миграции**: инвентаризация, анализ зависимостей и управления потоком, генерация транспортного каркаса, точки расширения для Java и проверка поведения. Универсальный автоматический компилятор ESQL не следует делать обязательным условием полезности продукта.

Camel пока разумно сохранить кандидатом для транспорта и оркестрации. Бизнес-правила, преобразования и обращения к БД должны находиться в обычных Java-сервисах, отделённых от Camel. Окончательный выбор между Camel и более простым Spring Boot приложением следует подтвердить одним сквозным пилотом с общей бизнес-реализацией.

## Что даёт и чего не решает Camel

Camel предоставляет транспортные компоненты и маршрутизацию; Java-методы можно вызывать из маршрутов через Bean Binding. Поэтому большое количество бизнес-логики на Java совместимо с использованием Camel. Само наличие крупного ESQL не является доводом за отказ от него. [Camel: Bean Binding](https://camel.apache.org/manual/bean-binding.html).

Camel не освобождает проект от определения соответствия деревьев сообщений, транзакций, исключений и выходов исходному поведению. Успешная генерация XML, компиляция Java или зелёные тесты на синтетическом корпусе не доказывают эквивалентность произвольного приложения.

Текущий конвертер, его парсеры, отчёты и регрессии полезны и при переносе бизнес-логики вручную. Расширять автоматическую генерацию следует только в пределах проверяемых правил.

## Варианты целевой реализации

Таблица содержит архитектурную оценку, а не результаты сравнительного нагрузочного теста.

| Вариант | Когда целесообразен | Стоимость и ограничения |
|---|---|---|
| Spring Boot + Camel + Java-сервисы | Существенная часть приложения — интеграционные маршруты: ветвления, несколько выходов, корреляция, разные адаптеры | Нужно освоить семантику Camel и проверить границы ошибок/транзакций; бизнес-логику всё равно переносить отдельно |
| Spring Boot + Spring JMS / Spring Kafka + Java-сервисы | Преобладают короткие цепочки «приём → обработка → отправка» | Меньше абстракций; сложную оркестрацию придётся явно писать и сопровождать |
| Spring Integration + Java-сервисы | Команда предпочитает Spring и её модель каналов, шлюзов и маршрутизаторов | Полноценная альтернатива для интеграционного слоя, но не средство автоматического переноса ESQL |
| Постепенный перенос с временным сохранением IIB/ACE | Нельзя заменить всё приложение одновременно; требуется ограничивать риск переключения | На переходном этапе нужно сопровождать две реализации и явно разделять владение обработкой |
| Полный автоматический ESQL → Java компилятор | Есть отдельный ресурс на разработку языка и среды совместимости, большой повторяемый корпус | Самый широкий объём: грамматика, функции, деревья, типы, исключения и транзакции; переносимый код всё равно требует проверки |

У Spring есть штатные средства JMS send/receive, JDBC и интеграционных паттернов: [Spring JMS](https://docs.spring.io/spring-framework/reference/integration/jms/using.html), [Spring Integration](https://docs.spring.io/spring-integration/reference/overview.html). Наличие этих средств не означает автоматического воспроизведения IIB.

## PROPAGATE и Java-обработчик

`PROPAGATE` передаёт управление нижележащей ветке синхронно. При успешном завершении этой ветки выполнение возвращается к следующему оператору ESQL. Ошибка ветки может прервать это продолжение. Это не оператор выхода из узла. `RETURN FALSE` в `Main` подавляет дополнительную автоматическую отправку; уже выполненные отправки сохраняют своё значение. [IBM: PROPAGATE](https://www.ibm.com/docs/en/app-connect/11.0.0?topic=statements-propagate-statement).

Из этого следуют два разных контракта Java-обработчика:

1. Если после обработки выбирается один выход, метод может вернуть результат с именем терминала, а адаптер вызовет нужный маршрут.
2. Если между отправками выполняются вычисления или обращения к БД, нужны синхронные вызовы выходных веток в соответствующих местах метода. Список выходов, который отправляется только после завершения метода, может изменить порядок эффектов и обработку ошибок.

Ниже — **псевдокод возможного адаптера**, а не существующий API проекта и не перевод исходного бизнес-примера:

```java
void handle(Input input, Outputs outputs) {
    var reference = referenceData.lookup(input.key());
    outputs.emit("out1", firstMapper.map(input, reference));
    var result = businessService.process(input, reference);
    outputs.emit("out", result);
}
```

`emit` в таком контракте должен дождаться выполнения связанной ветки и вернуть её ошибку вызывающему коду. Для вывода в очередь это не означает ожидания обработки сообщения внешним получателем. Отдельно нужно задать отсутствие неявной отправки после завершения метода.

В Camel для вызова внутренних маршрутов есть синхронный `direct:`. Однако одного его использования недостаточно: требуется проверить обработчики ошибок, используемый поток выполнения, транзакцию и состояние сообщения. [Camel: Direct](https://camel.apache.org/components/4.22.x/direct-component.html).

При переносе также учитываются `DELETE`, `FINALIZE`, Compute Mode и выбор деревьев сообщения. Копирование `Exchange` само по себе не воспроизводит их поведение. Модель адаптера должна поддерживать только явно заявленный профиль. [IBM: несколько выходных сообщений](https://www.ibm.com/docs/en/app-connect/12.0.x?topic=content-generating-multiple-output-messages).

## Как переносить большой ESQL

Первым переносится один завершённый сценарий с его вызываемыми процедурами и зависимостями. Сначала полезно сохранить понятную последовательность действий, затем выделять повторяемые преобразования и правила в сервисы. Делать отдельный микросервис на каждый Compute или подпоток не требуется.

Рекомендуемые границы внутри приложения:

- транспортный адаптер: сообщение, технические заголовки, корреляция, ошибка доставки;
- прикладной обработчик: порядок действий и решение о выходах;
- бизнес-сервисы: проверки, расчёты, преобразования;
- слой доступа к данным: параметризованные запросы и отображение результатов;
- сериализация: согласованный формат XML/JSON и кодировки.

JDBC подходит для справочников и явных запросов: `JdbcClient`/`JdbcTemplate` предоставляют запросы и отображение строк. JPA выбирается при необходимости модели сущностей, а не из-за длины ESQL. [Spring JDBC](https://docs.spring.io/spring-framework/reference/data-access/jdbc/core.html).

Модель данных можно вводить постепенно. Не обязательно сразу создавать Java-сущность для каждого элемента XML. При этом требуется явно проверять пространства имён, повторяющиеся элементы и различия между отсутствующим, пустым и null-значением.

Если сценарий изменяет БД и отправляет сообщения, нужно отдельно согласовать атомарность. Одна аннотация `@Transactional` не гарантирует общую транзакцию JDBC/JMS/Kafka. В частности, синхронизация JDBC и Kafka предполагает последовательные commit и допускает отказ второго после первого. Выбор XA, outbox или компенсации определяется исходным контрактом. [Spring Kafka: transactions](https://docs.spring.io/spring-kafka/reference/kafka/transactions.html).

## Ближайшая проверка направления

1. Выбрать один законченный сценарий: вход, зависимые подпотоки и процедуры, доступ к данным, все выходы и ошибки. Не обязательно начинать с самого большого модуля.
2. Описать контракт и подготовить входы, состояние справочников, ожидаемые сообщения, ошибки и эффекты. Проверять не только текст ответа, но количество/порядок отправок, свойства и повторы.
3. Реализовать Java-обработку без привязки бизнес-сервисов к Camel. При возможности сравнить с запуском IIB на одинаковых тестовых данных; без такого запуска явно ограничить достоверность проверки.
4. Подключить Camel как тонкий транспортный слой и оценить, сколько полезной оркестрации он берёт на себя. Для того же обработчика сопоставить сложность обычного Spring listener; не переписывать всю систему ради сравнения.
5. По результатам закрепить стек и профиль генерации. Автоматизировать повторяемые, доказанные операции.

ESQL нельзя полностью отложить до завершения генератора топологии. Уже сейчас необходимо понимать управление потоком: `PROPAGATE`, `RETURN`, `THROW`, окружающие условия/циклы и вызываемые процедуры. Детальный перенос остальных бизнес-правил можно выполнять поэтапно.

Без полного сценария и ожидаемого поведения фотографии позволяют оценить характер задачи, но не дают достоверной оценки сроков или доли автоматизации. Размер в строках также недостаточен: важнее зависимости, разнообразие конструкций, транзакции и доступность проверок.

## Последствия для текущей разработки

Расширение генератора сервиса и отдельного интерпретатора графа приостановлено на время этой оценки. Добавлять собственный движок исполнения поверх Camel до выявления конкретной неподдерживаемой семантики не рекомендуется: это создаёт ещё одну среду, которую придётся доказывать и сопровождать.

Полезные следующие возможности конвертера — достоверный анализ топологии и параметров экземпляров, связь с ESQL-модулями, инвентаризация зависимостей и точек передачи управления, явные Java-заготовки и проверка результатов. Каркас с заглушками должен отличаться в отчёте от сценария с реализованной и проверенной бизнес-логикой.

Сквозной пилот с исходной средой, реальными зависимостями и транспортным контрактом пока не выполнен. Локальный эксперимент с ручным Java-переносом и адаптерами не считается автоматической конвертацией или доказательством эквивалентности IIB. Смена Camel на другой стек и расширение поддерживаемого ESQL не объявлены реализованными или утверждёнными.
