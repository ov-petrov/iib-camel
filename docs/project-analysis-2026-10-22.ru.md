Назначение документа: рабочая основа для исправлений, уточнения требований и планирования следующих итераций. Это анализ текущей реализации, а не утверждение новой спецификации. Предлагаемые параметры CLI, архитектурные сущности и критерии приёмки ниже ещё не реализованы и не согласованы.

## 1. Вывод и рекомендуемый порядок работы

Проект уже представляет собой работающий прототип: есть два Maven-модуля, автономный CLI, разбор потоков и ограниченного подмножества ESQL, диаграммы, отчёты, генерация XML/Java и исполняемый Spring Boot runtime. Штатная сборка успешна: **92 теста, 0 failures, 0 errors, 0 skipped**.

Главный риск — **конвертер может изменить поведение исходного потока, при этом отметить преобразование как полное**. Это подтверждено отдельными воспроизведениями. Например, свежий результат конвертации базового `corr-01` направляет корректное HIGH-сообщение в очередь ошибок; штатный e2e проходит благодаря ручному Compute-бину. Другие примеры: потеря условий ESQL, замена числового равенства на `>`, потеря строк Route-таблицы, пропуск вложенного подпотока.

Первую следующую итерацию рекомендую посвятить достоверности: устранить ошибки базового сценария, запретить признание непонятой логики полностью переведённой и проверять именно свежесгенерированные артефакты. После этого — закрывать выбранный объём Must: подключение IBM MQ, обработку ошибок, необходимые узлы и модели/MapStruct.

Текущую готовность нельзя корректно выразить одним процентом. Процент из migration-report отражает применённые правила к выбранным единицам, а не доказанную эквивалентность бизнес-логики, готовность к эксплуатации или долю выполненных FR.

## 3. Текущее устройство и полезные наработки

```text
                       ┌─ analyze → Mermaid / AsciiDoc / Markdown
IIB-файлы → парсеры → IR┤             + ESQL inventory
                       └─ convert → Camel XML + Java beans/models
                                      + migration-report.md
                                              │
                                      ручной перенос файлов
                                              ↓
                         runtime: Spring Boot + Camel + Artemis
```

- `converter`: picocli, стандартный XML DOM, простые Java records для IR, ESQL на регулярных выражениях; Spring-контекст конвертеру не нужен.
- `runtime`: загрузка XML с classpath, JMS-компонент, embedded Artemis по умолчанию, ручной `AdapterCompute1`, сгенерированный `CheckCompute1`, базовый `AbstractComputeBean`.
- Корпус `corr-01` проверяет адаптер с Route и catch; `corr-02` — один уровень подпотока; `corr-03` — генерацию части ESQL и моделей без исполнения в runtime.
- Парсер потоков общий для анализа и конвертации. Разделение IR и рендереров — хорошая основа для развития.
- Сохранены golden-файлы, отчёты по узлам, детерминированный порядок основных операций, комментарии исходных ESQL-операторов. Это полезно для регрессии и ручной миграции.
- Архитектура пока рассчитана на небольшие примеры: реестра целого проекта, модели символов/типов и стадии семантической валидации нет. Основная логика сосредоточена в `RouteGenerator` и `ConvertCommand`.

### BUG-01. Свежий `corr-01` не выполняет заявленную маршрутизацию

**Воспроизведение.** Выполнить `convert` для `corr-01-simple-adapter`, скомпилировать его `AdapterCompute1.java` и выполнить полученный маршрут на `order-high.xml`. В диагностике заменены только JMS URI на `direct:` и добавлены получатели, записывающие выбранную ветку:

```text
corr01-handwritten:     [ADAPTER.PRIORITY.Q]
corr01-fresh-generated: [ADAPTER.ERROR.Q]
```

**Причина.** [Ручной бин][src-manual-bean] парсит тело в `Adapter`, а сгенерированный бин оставляет `String`. [Генератор Route][src-route-predicate] создаёт `${body.order.status}`. У строки нет свойства `order`; Camel выбрасывает `RuntimeBeanExpressionException`, который уходит в `doCatch`.

**Предложение.** Согласовать единый контракт тела: XML/DOM + XML-предикаты либо явный переход в сгенерированную типизированную модель с обратной сериализацией. Для первого ограниченного XML-MVP целесообразно изучить прямое сохранение XPath-семантики Route, поскольку сейчас готовой универсальной POJO-модели нет. Преобразование XPath-переменных IIB и namespaces должно быть явным, а не простой заменой строки.

**Критерий исправления.** Чистая генерация `corr-01` → компиляция → загрузка маршрута → все три сценария проходят без ручного `AdapterCompute1`; отдельно проверено отсутствие сообщений в неверных очередях. Порядок копирования generated-файлов не должен создавать два Spring-бина `adapterCompute1`.

### BUG-02. Парсер ESQL не сохраняет структуру программы

**Воспроизведено:**

```sql
IF TRUE THEN
  SET OutputRoot.MQMD.A = 'A';
  SET OutputRoot.MQMD.B = 'B';
ELSE
  SET OutputRoot.MQMD.C = 'C';
END IF;
```

Первый SET остаётся внутри TODO, а `B` и `C` превращаются в **безусловные** Java-вызовы. В `CASE` присваивания всех ветвей переводятся последовательно, при этом `complete=true`. `RETURN FALSE` игнорируется и модуль также считается полностью переведённым. Строка `-- SET OutputRoot.MQMD.Hidden = 'EXECUTED';` порождает исполняемое присваивание. `DECLARE` исчезает без диагностики; произвольный непустой текст вместо ESQL даёт пустой список модулей и успешный `analyze`.

**Причина.** [EsqlParser][src-esql-parser] ищет подстроки регулярными выражениями. Неподдерживаемая ветвь ограничивается ближайшей `;`, комментарии и лексические контексты не выделены. [EsqlTranslator][src-esql-translator] не использует `returnsTrue` для поведения/полноты.

`RETURN FALSE` действительно подавляет итоговую автоматическую отправку Compute; это часть семантики, а не необязательная подсказка генератору. [IBM ACE: generating multiple output messages](https://www.ibm.com/docs/en/app-connect/12.0.x?topic=content-generating-multiple-output-messages).

**Предложение.** Сначала консервативно ограничить перевод: любой нераспознанный исполняемый фрагмент или неизвестная структура блока исключает статус полного перевода; содержимое неподдерживаемого блока не вынимать наружу. Затем ввести токенизацию комментариев/литералов и AST для явно выбранного подмножества. Сохранять полный исходный диапазон неподдерживаемой конструкции.

**Критерий исправления.** IF с несколькими SET, ELSE/ELSEIF, вложенные блоки, CASE, RETURN TRUE/FALSE, PROPAGATE, комментарии и неизвестный оператор имеют поведенческие тесты. Для пока неподдерживаемого случая — диагностируемый отказ/заглушка всего блока, без ложного `converted` и без исполнения его отдельных строк.

### BUG-03. Route теряет таблицу условий и меняет операции сравнения

**Воспроизведено.** Добавление второй строки `filterTable` LOW после HIGH заменяет условие HIGH; оба `<when>` получают LOW. Числовое `$Body/Order/amount=100` превращается в `${body.amount} > 100`. Для `>100` генерируется `TODO simple for: …`, но статус узла остаётся `CONVERTED`; для `>=100` получается `${body.amount>} > 100`.

**Причина.** [MsgFlowParser.node][src-flow-node] складывает повторяющиеся дочерние элементы в один `Map<String,String>` с одинаковыми ключами. [emitChoice][src-route-choice] обходит динамические терминалы и применяет одну строку ко всем. [toSimple][src-route-predicate] ищет только первый `=` и выбирает оператор по наличию кавычки у значения.

По коду также отсутствует учёт `distributionMode`: всегда используется `choice`, то есть выбирается одна ветвь. У IBM Route таблица задаёт порядок и связь условия с терминалом, а режимы `First` и `All` имеют разное поведение; выражения Route — **XPath**, их нельзя считать просто строковыми ESQL-сравнениями. Это подтверждено документацией ACE 13; точный целевой профиль IIB/ACE ещё требуется закрепить. [IBM ACE: Route node](https://www.ibm.com/docs/en/app-connect/13.0.x?topic=nodes-route-node).

**Предложение.** Хранить упорядоченный `List<RouteRule>` с выражением, терминалом и источником; отдельно хранить distribution mode. Использовать проверяемое преобразование поддерживаемого языка предикатов, неизвестные выражения маркировать как непереведённые.

**Критерий исправления.** Два и более правила, несколько правил на терминал, First/All, Default, unmapped terminal, `=`, `!=`, `<`, `<=`, `>`, `>=`, строки/числа и namespaces проверяются на наборах сообщений и числе отправок.

### BUG-04. Операции над деревом сообщения не соответствуют их ESQL-путям

**Воспроизведено.** Для входа `<Order><Status>NEW</Status></Order>` и пути `OutputRoot.XMLNSC.Order.Status` результат:

```xml
<Order><Status>NEW</Status><Order><Status>DONE</Status></Order></Order>
```

[setBodyField][src-runtime-body] начинает обход с существующего XML-корня и повторно создаёт первый сегмент `Order` как ребёнка. Текущий unit-тест закрепляет другую договорённость: путь без XML-корня, которой генератор не следует. В ESQL путь после XMLNSC включает элементы XML-дерева; примеры IBM используют `OutputRoot.XMLNSC.Target...`. [IBM: message tree copying](https://www.ibm.com/docs/en/integration-bus/9.0.0?topic=tree-message-copying).

Дополнительно воспроизведено: `OutputRoot.JSON.Data.status = 'READY'` считается полностью переведённым, но вызывает XML-парсер и падает на JSON. Вызов `copy()` после модификации не восстанавливает исходное тело: это no-op. Отдельных InputRoot и OutputRoot в runtime нет. Случай «копирование единственным первым действием» существенно уже общей семантики SET.

**Предложение.** Зафиксировать модель дерева и границы поддержки доменов; для XML учитывать корень, namespaces, атрибуты и коллекции. JSON либо реализовать отдельным адаптером, либо честно исключить из перевода. Для копирования сохранять независимый входной снимок или разрешать оптимизацию no-op только при доказанных условиях. Необходимость создавать OutputRoot зависит также от Compute Mode. [IBM ACE: Compute node](https://www.ibm.com/docs/en/app-connect/13.0.x?topic=nodes-compute-node).

**Критерий исправления.** Тесты корня и вложенных элементов, повторного SET OutputRoot, работы без предварительного copy, пустого тела, namespaces и JSON. Неподдерживаемый домен не получает `converted`.

### BUG-05. Вложенные подпотоки и qualified names

**Воспроизведено.** Для Parent → Sub → Inner генерируется `to direct:Inner`, но отсутствует маршрут-потребитель Inner. Для ссылки `Schema_Check` и существующего `Schema_Check.subflow` генерация падает с `NullPointerException`. При ненайденном подпотоке прекращается обход последующего `out`, хотя комментарий к генератору обещает продолжение.

**Причина.** [inlineRouteXml][src-subflow] теряет собранные вложенные ссылки, а вызывающая сторона заново получает подпоток по укороченному ключу, который может отсутствовать в реестре. Ограничение глубины не реализует полноценную проверку графа зависимостей. По коду входные/выходные терминалы подпотока тоже не моделируются как самостоятельные точки: все Input объединяются, Output просто возвращает управление.

**Предложение.** До генерации строить граф зависимостей и разрешать ссылки в канонические IDs; затем выдавать каждый подпоток один раз в пределах поставляемого набора маршрутов. Для нескольких терминалов определить контракт или отказ от автоматической конвертации.

**Критерий исправления.** 2–3 уровня вложенности, повторное использование одним/несколькими родителями, одинаковые короткие имена в разных схемах, отсутствующая ссылка и цикл зависимостей. Для каждого `direct:` существует ровно ожидаемый потребитель; нет NPE и скрытого обрезания цепочки.

### BUG-06. Обход графа теряет связи и не останавливает циклы

**Воспроизведено.** Две связи из одного `out` → генерируется только первая. `MQOutput → MQOutput` → второй узел пропущен. `Compute.out → тот же Compute` → `StackOverflowError`. Пропущенные узлы в первых двух случаях помечаются partial с неверным объяснением «нет пути», хотя путь существует.

**Причина.** [walk/connection][src-route-walk] выбирают `findFirst`, `visited` используется для отчёта, но не для защиты рекурсии; MQOutput завершает обход без перехода по своему `out`.

**Предложение.** Валидировать граф до генерации: доступность, количество связей, поддерживаемые терминалы, циклы. Для поддерживаемого fan-out сохранять каждую отправку и согласованную семантику копирования/ошибок. Не заменять граф произвольным параллельным multicast без анализа порядка IIB.

**Критерий исправления.** Ни одно ребро не исчезает без отдельной диагностики; цикл завершается контролируемой ошибкой с путём цикла; отдельно проверены fan-out, общий downstream, несколько MQOutput подряд и неизвестные терминалы.

### BUG-07. Обработчики ошибок преобразуются неверно

**Воспроизведено.** Ветка `MQInput.catch → Compute → MQOutput` превращается в отправку `jms:TODO-queue-not-set` вместо вызова Compute и продолжения цепочки.

**Причина.** [catchBranch][src-route-catch] предполагает, что непосредственный приёмник catch/failure всегда очередь, выбирает первую из двух веток и останавливается. Терминалы failure у Compute/Route и другие локальные обработчики в основном обходе не исполняются как обработчики.

**Предложение.** Описать область перехвата исключений и различие catch/failure для выбранных узлов. Генерировать полноценные ветки с обычным обходом, а политику ошибок runtime согласовать с локальными обработчиками. У `doTry/doCatch` в Camel собственная область обработки, поэтому будущую глобальную DLQ нельзя добавлять без проверки их взаимодействия. [Apache Camel: Try, Catch and Finally](https://camel.apache.org/manual/try-catch-finally.html).

**Критерий исправления.** Ошибка в Compute/Route, ошибка входного разбора, цепочка в catch, обе ветки catch/failure, ошибка самого обработчика, fallback DLQ и повторная доставка имеют отдельные ожидаемые результаты. Последняя формулировка — требования к будущим тестам, а не утверждение о уже проверенной доставке.

### BUG-08. Отчёт не проверяет разрешение Compute-ссылок

**Воспроизведено.** Конвертация только `Adapter.msgflow`, без его ESQL: exit 0, все 6 узлов converted, отчёт даёт 100%; бин не создан. Сам `computeExpression` считается достаточным основанием для `CONVERTED`.

**Причина.** [ConvertCommand][src-convert] независимо обрабатывает потоки и ESQL, а [diagnoseCompute][src-compute-diagnosis] не связывает узел с реально найденным модулем и результатом его генерации. Параметр `--input` с одиночным `.msgflow` не подтягивает соседние зависимости автоматически.

**Предложение.** Реестр символов «проект/схема/модуль/функция», явный корень разрешения зависимостей, проверка bean/direct/schema references. Если бин намеренно поставляется вручную — нужен явный контракт внешней зависимости и соответствующий статус, а не молчаливый успех.

**Критерий исправления.** Отсутствующий модуль, неверная функция, частично переведённый модуль и конфликт имён отражаются на готовности использующего их маршрута. 100% converted невозможно получить при неразрешённой обязательной ссылке.

### BUG-09. Коллизии имён приводят к перезаписи и неоднозначности

**Воспроизведено.** Два разных `.msgflow` с одинаковым `nsURI` дают один route-файл: второй перезаписывает первый, exit 0, в статистике учтены оба. Два MQInput внутри одного потока создают два `<route>` с одинаковым ID.

По коду аналогичные риски есть для ESQL-модулей с одинаковым именем в разных схемах, моделей `Order` из разных модулей и одного подпотока, включённого в XML нескольких родителей. Эти разновидности коллизий выявлены чтением кода, отдельные runtime-запуски для них не проводились.

**Предложение.** Отделить исходное имя, канонический ID и безопасное имя выходного файла. Использовать namespace проекта/схемы, фиксировать коллизии до записи; модели объединять только по явному правилу совместимости. Выходной manifest должен связывать источник и результат.

**Критерий исправления.** В пакетной обработке не теряется ни один артефакт; IDs маршрутов/бинов уникальны в целевом приложении. Повторная генерация детерминирована и не оставляет устаревшие маршруты без маркировки/удаления по manifest.

### BUG-10. Синтаксическая корректность выходных артефактов не гарантирована

**Воспроизведено.** Значение входного XML-атрибута с `&amp;` восстанавливается парсером в `&`, после чего попадает в Camel XML без экранирования. Выходной файл не разбирается XML-парсером, но конвертация успешна. Поле `OutputRoot.XMLNSC.Order.class` порождает `private String class;` и `class()`: `javac` завершается с ошибкой.

**Причина.** XML собирается конкатенацией строк в [RouteGenerator][src-route-walk], Java-идентификаторы формируются из исходных имён без общей политики в [EsqlToJavaGenerator][src-java-model]. Нет проверки сгенерированного набора. По коду также не обеспечены JavaBean getters: для Status создаётся `Status()`, а не `getStatus()`; это требует исправления до подключения MapStruct. Наличие компилируемого исходника само по себе не доказывает пригодность модели для маппера.

**Предложение.** XML writer с корректным escaping; единая нормализация Java-имён и таблица обратного соответствия исходным полям, корректные getter/setter. Валидация Camel на фактической версии runtime и компиляция всех файлов одной генерации.

**Критерий исправления.** Спецсимволы XML, кавычки, `--` в комментариях, Unicode, Java keywords и нормализующиеся в одинаковое имя идентификаторы дают корректный результат или точную диагностику. Модели проходят JavaBeans/MapStruct-проверку.

### BUG-11. Выход за пределы каталога результатов

**Воспроизведено безопасно во временном каталоге.** Входное `nsURI="../escaped.msgflow"` приводит к записи `escaped-route.xml` на уровень выше `--output`. Аналогично `analyze` создаёт там `escaped.md` и другие форматы. Обе команды возвращают 0.

**Причина.** [ConvertCommand][src-convert] и [AnalyzeCommand][src-analyze-write] передают имя из входа в `Path.resolve` без проверки границ, [DiagramNames][src-diagram-names] только убирает расширение. Права ОС ограничивают итоговый ущерб, но это не обеспечивает обещанный каталог вывода.

**Предложение.** Никогда не трактовать внешнее имя артефакта как путь. Назначать безопасные имена, проверять нормализованный путь и символьные ссылки, заранее проверять конфликты. Не перезаписывать несвязанные пользовательские файлы.

**Критерий исправления.** Относительные переходы, абсолютные имена и вывод через symlink не выходят за разрешённый корень. Для проверки используются только тестовые файлы во временном каталоге.

### BUG-12. XML сообщения может загружать внешний DTD

**Воспроизведено.** Временный локальный DTD объявлял default-атрибут `sentinel="LOADED_LOCAL_DTD"`; после `setBodyField` атрибут появился в сообщении. Значит, runtime прочитал ресурс, указанный во входном DOCTYPE. Доступ к секретным файлам и внешним адресам не проверялся.

**Причина.** [AbstractComputeBean][src-runtime-body] задаёт только `setExpandEntityReferences(false)`, что не запрещает загрузку внешнего DTD.

**Предложение.** Централизованная фабрика XML с запретом DOCTYPE/внешних entities и DTD, `ACCESS_EXTERNAL_DTD`/`ACCESS_EXTERNAL_SCHEMA`, ограничениями размера и сложности. Применять к каждому входному XML-пути с учётом его библиотек; не объявлять весь проект уязвимым по результату одной фабрики. Для `MsgFlowParser` уже включён secure processing, его поведение нужно проверять отдельно.

**Критерий исправления.** XML с внешним DTD отклоняется без обращения к ресурсу; обычный XML и namespaces продолжают работать; отказ имеет диагностируемый маршрут обработки.

### BUG-13. ESQL-строки и выражения теряют значение

**Воспроизведено.** `'O''Brien'` превращается в Java-строку с двумя апострофами. Выражение `'a' || 'b'` считается одним литералом и становится текстом `a' || 'b`, статус — полный перевод. В `'a;b'` парсер обрезает оператор на внутренней точке с запятой: оставшаяся часть исходного выражения не сохраняется как полный оператор.

Для ESQL удвоенная кавычка внутри литерала означает одну кавычку. [IBM IIB: ESQL CHARACTER data type](https://www.ibm.com/docs/en/integration-bus/10.0.0?topic=types-esql-character-data-type).

**Предложение.** Общий лексический разбор для BUG-02 и BUG-13; строго различать литерал и выражение. CAST обрабатывать с реальными типами/ошибками либо маркировать как приближение: текущая запись типа в примечании не равна проверке значения.

**Критерий исправления.** Кавычки, разделители внутри строк, конкатенация, пустые значения, многострочный исходник, Unicode, корректные и некорректные CAST не искажаются. Неподдерживаемое выражение сохраняется полностью и не получает статус полного перевода.

### BUG-14. Валидация структуры и namespaces недостаточна

**Воспроизведено.** Замена только namespace-префикса `xmi` на другой при неизменном URI делает корректный XML неразбираемым: «узел без xmi:type». Два одинаковых `xmi:id` принимаются командой `analyze` без ошибок.

**Причина.** [MsgFlowParser][src-flow-parser] включает namespace awareness, но читает `getAttribute("xmi:type")`, `getAttribute("xmi:id")` и ряд элементов по буквальному имени. Проверки уникальности и целостности графа нет; IR не хранит source spans. Это расходится также с D-2 из дизайна диаграмм.

**Предложение.** Использовать namespace URI + local name, выделить семантическую валидацию IR и сохранить источник каждого узла/ребра/оператора. Для неизвестной, но корректной структуры — явная диагностика вместо молчаливого пропуска.

**Критерий исправления.** Изменение XML-префикса не меняет IR; duplicate ID, dangling edge и некорректный терминал обнаруживаются с файлом и местом. Для структур без поддержки выбирается документированная политика.

### BUG-15. Нарушения CLI-контракта

**Воспроизведено:**

1. `analyze --input path/to/Adapter_Compute1.esql` возвращает 1: сборщик потоков отклоняет `.esql` до вызова сборщика ESQL, хотя одиночный ESQL заявлен в описании команды.
2. Один корректный msgflow + один повреждённый ESQL создают маршрут и отчёт, но `convert` возвращает **3**, означающий «ничего не обработано». В [ConvertCommand][src-convert-exit] сравниваются общее число ошибок и количество msgflow.

По коду `--fail-fast` в analyze прекращает только цикл потоков; ESQL всё равно обрабатывается. `collect()` у convert скрывает ошибки чтения под пустым списком. Повторное использование экземпляра ConvertCommand сохраняет предыдущие счётчики и списки — это ограничение будущего Java API, не основной one-shot CLI-сценарий.

**Предложение.** Общее обнаружение входов, раздельные счётчики успешных/ошибочных файлов, неизменяемый результат одного запуска, единый документированный набор exit codes. Отдельно согласовать будущий strict-режим: сейчас код 0 при partial/unsupported сам по себе соответствует существующей политике «обработка завершена» и не является автоматически ошибкой CLI.

**Критерий исправления.** Таблица тестов для файла/каталога каждого типа, пустого/отсутствующего/недоступного входа, смешанного результата, всех ошибок, ошибки записи отчёта и fail-fast. Один и тот же контракт приведён в help, RU/EN документации и тестах.

### 6.2. Решения о поведении, которые нужны для реализации

1. **Версии и границы источника.** Какой IIB/ACE и какой Toolkit-export обязательны? Только исходные проекты или также BAR? Какие libraries/shared libraries/broker schemas? Начать с обезличенного реального корпуса и выбрать один явный профиль; поддержку BAR не считать подразумеваемой.
2. **Определение MVP.** Выбрать между узким «MQ + XMLNSC + линейный Compute + Route + single-entry/single-exit subflow» и всем текущим Must. Рекомендация — первый профиль как проверяемый пилот, но только после явного пересмотра MoSCoW.
3. **Тело и ULM.** Что хранится в Exchange: исходные bytes, String, DOM, JSON tree, типизированный объект? Где Properties, MQMD, Environment, LocalEnvironment, ExceptionList и DestinationList? Как задаётся Compute Mode? Не сводить всё к headers без таблицы семантики.
4. **Эквивалентность сообщений.** Для XML сравниваем дерево с сохранением namespaces/атрибутов/значимых пробелов или исходные байты? Для подписи, mixed content, encoding/CCSID может требоваться байтовая сохранность. Для JSON определить порядок, числа, null и отсутствующие поля.
5. **ESQL-подмножество.** Перечислить операторы и выражения в грамматике, включая RETURN/PROPAGATE, типы, NULL, cardinality, индексы, CASE/IF и исключения. Неподдержка должна диагностироваться даже до появления реализации соответствующей функции.
6. **Маршрутизация.** Зафиксировать XPath-профиль Route, First/All, связь правил и терминалов, fan-out и порядок выполнения. Для Filter определить TRUE/FALSE/UNKNOWN/failure, если эти терминалы входят в выбранный профиль.
7. **Подпотоки и имена.** Разрешение по схеме/проекту, несколько входов/выходов, recursion, переиспользование, свойства экземпляров. Вход одиночным файлом должен иметь явный dependency root или отчёт о недостающих файлах.
8. **IBM MQ.** Нужны параметры queue manager/channel/host/port/TLS/auth, типы сообщений, mapping MQMD↔JMS, корреляция, reply-to, persistence/TTL/priority и CCSID. Текущая проверка свойства `ApplicationIdData` на Artemis не доказывает изменение одноимённого поля MQMD в IBM MQ. `CommentField` в фикстурах также нельзя считать доказательством реального MQMD-контракта.
9. **Ошибки и доставка.** Что означает успешная обработка/ACK, когда rollback/redelivery, сколько попыток, куда DLQ, что сохраняется при ошибке, как избежать повторных побочных эффектов? XA уже исключён, но локальную политику доставки всё равно требуется определить.
10. **Частичная миграция.** Заглушка только логирует и продолжает, останавливает маршрут или запрещает deployment? Рекомендация: отдельный режим заготовок для инженера и запрет промышленной сборки с неразрешёнными обязательными блоками. Предлагаемый `--strict` — новая функция.
11. **Повторная генерация и ручной код.** Кто владеет generated-файлами, как сохраняются ручные исправления, удаляются устаревшие артефакты и обнаруживаются конфликты? Рекомендация: generated-код отдельно, ручные реализации через явные extension points, manifest результата.
12. **Модель поставки.** Один runtime на весь набор потоков или приложение на интеграцию? Подключение generated library или генерация отдельного проекта? Это влияет на идентификаторы, конфигурацию, release cycle и изоляцию отказов.
13. **Нефункциональные границы.** Размер/число файлов и сообщений, время/память конвертации, глубина графов, параллельность, безопасный XML и вывод, детерминированность, воспроизводимость JDK/Maven. Цифры следует получить на реальном корпусе, а не назначать произвольно.

Все эти вопросы допускают предварительные решения для пилота. Они не должны тормозить исправление уже подтверждённых BUG-01/02/03 и защиту файлов/парсеров.

## 7. Предлагаемые доработки архитектуры

Развитие можно выполнять внутри существующих модулей; немедленный переход к множеству Maven-модулей не требуется.

```text
Discovery → Parse + source spans → Project IR + symbols
                                      ↓
                          Resolve + validate + capabilities
                                      ↓
                             Conversion plan
                          ┌───────────┼───────────┐
                       Camel XML    Java       Report/manifest
                          └───────────┼───────────┘
                              Compile/load checks
                                      ↓
                                Runtime tests
```

| Доработка | Зачем | Минимальный результат |
|---|---|---|
| `SourceRef(file,line,column,end)` | Достоверная диагностика и ручная доработка | Каждый узел, ребро и ESQL-конструкция имеют исходный диапазон |
| Project IR / symbol table | Межфайловые ссылки и уникальность | Qualified IDs для потоков, схем, модулей и функций |
| Типизированные RouteRule и терминалы | Сохранение графа | Повторяющиеся правила не теряются в Map |
| Лексер и ограниченный ESQL AST | Исправление семантики | Statements/expressions/unknown blocks с точными границами |
| Capability registry | Общие ответы analyze/convert | Статус зависит от свойств/выражений/зависимостей, а не только имени типа |
| ConversionPlan | Разделение генерации и принятия решений | Все ссылки и запланированные файлы известны до записи |
| Report + manifest | Отчётность и повторная генерация | Исходник → артефакт, ограничения, версии правил, результат валидации |
| Output writer | Защита результатов | Escaping, collision checks, запись только внутри корня, контролируемая замена |
| Публичный ConversionService | CLI и будущий API | Новый независимый результат на каждый запуск; CLI лишь адаптирует параметры |

Не рекомендую сейчас расширять список узлов большим switch без проверки семантики. Сначала отделить capability-check и graph traversal, затем добавлять один законченный сценарий за раз.

MapStruct целесообразно вводить после решения по моделям и типам: сначала «поле → поле» из согласованного формата Mapping, затем константы/defaults/type conversions. Генерировать интерфейс `@Mapper(componentModel = SPRING)`, реализацию получать annotation processor; компилируемость и Spring-discovery проверять автоматически. Полный императивный ESQL не следует принудительно сводить к MapStruct.

## 8. Как усилить тестирование

### 8.1. Почему текущие зелёные тесты недостаточны

- Golden-тесты преимущественно сравнивают текст побайтово. Заявленные в стратегии XML-канонизация, сравнение графа и поведенческий oracle для предикатов пока не реализованы.
- Runtime исполняет сохранённые ресурсы. Свежий запуск converter и компиляция его результатов не являются шагами Maven-тестов. Ручной бин в `corr-01` скрывает BUG-01.
- `corr-03` проверяет текст результата, но не исполняет изменение тела; поэтому ошибочная трактовка XML-корня закреплена тестом helper-метода.
- `E2eDatasetTest` проверяет ожидаемую очередь, но не отсутствие сообщения в остальных и не отсутствие дубликатов. Очереди очищаются перед всем методом, а не перед каждым YAML-кейсом.
- Сравнение XML через `replaceAll("\\s+", "")` стирает значимые пробелы в данных и может пропустить изменение, например `"A B" → "AB"`.
- Пять сценариев запущены в одном тестовом методе с жёстким `assertEquals(5, passed)`: новый датасет требует изменения Java, ошибка раннего кейса обрывает оставшиеся.
- Нет проверок generated compile/load для произвольных входов, транзакций/отказа брокера, реального IBM MQ, полного Must-каталога.
- В этом репозитории не найдены собственные CI workflow и Maven Wrapper. Наличие тестовой стратегии не означает наличие CI enforcement.
- Тест `bareRunUsesDefaultInputAndOutputDirectories` использует настоящие `converter/input` и `converter/output`, затем рекурсивно удаляет их. Это выявлено чтением теста, специально с пользовательскими файлами не воспроизводилось. Такой тест нужно изолировать в temp working directory.

### 8.3. Предлагаемая организация

1. Unit: parser/IR/resolver/translator, включая отказ для неподдерживаемой конструкции. Для каждого бага добавлять тест на различимое бизнес-поведение или контракт.
2. Golden: детерминированность и ревью артефактов сохранять, но не считать доказательством смысла. Изменение golden должно сопровождаться объяснением ожидаемого поведения.
3. Generated integration: генерировать в temp, компилировать на закреплённом runtime classpath, загружать весь набор. Для XML проверять Camel loader, а не только well-formedness.
4. Runtime datasets: отдельный параметризованный/динамический тест на кейс, уникальные очереди или корреляционные IDs, проверка нужных и ненужных выходов, количества сообщений и значимых данных.
5. IBM MQ profile: отдельная явно подключаемая среда, не подменять её Artemis. При отсутствии среды отражать skipped/not-run, а не считать интеграцию успешной.
6. PR pipeline: `verify` + fresh generation/compile/load + короткие поведенческие наборы. Полный корпус/нагрузка/брокерные отказы можно выделить в более редкие запуски.

Измерение покрытия добавить как вспомогательный сигнал; ключевой gate — поддерживаемая возможность имеет fixture, ожидаемые статусы и поведенческий тест. Полного эмулятора IIB для этого не требуется; эталоны следует получать из подтверждённых контрактов и, для критичных сценариев, согласованного запуска на ACE вне обязательного локального CI.

### Критерии готовности первого пилота

- Утверждены профиль исходных файлов/узлов/ESQL и значение статуса «готово к запуску».
- Нет открытых P0 для выбранного профиля; P1, способные потерять данные/артефакты или нарушить файловые границы, закрыты.
- Свежая генерация без ручной подмены проходит compile/load и датасеты, включая отрицательные выходы.
- Все неизвестные конструкции, неразрешённые ссылки и ограничения перечислены с источником; недоказанная часть не увеличивает готовность.
- Настроены и проверены целевой брокер, ошибки и подтверждения доставки, если пилот включает IBM MQ.
- Повторная генерация не перезаписывает ручной код и не оставляет незаметно старые маршруты.
- Руководство воспроизводится на чистом рабочем каталоге.
