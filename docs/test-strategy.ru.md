# Стратегия тестирования проекта iib-camel

> 🇬🇧 English version: [test-strategy.en.md](test-strategy.en.md)

> Функциональные требования: [functional-requirements.ru.md](functional-requirements.ru.md)

Текущее состояние автоматизации и результаты первой итерации: [ход реализации](implementation-progress.ru.md). Fresh-generation/compile/runtime-проверки уже выполняются в `mvn verify`; сравнение графов и полный поведенческий oracle ниже остаются планом, а не существующей реализацией.

## 1. Цель и принципы

Задача тестирования — доказать, что:

1. **Конвертер** создаёт семантически эквивалентные артефакты: сгенерированный маршрут Camel
   «делает то же самое», что исходный поток IIB;
2. **Runtime-сервис** маршрутизирует сообщения туда же и с таким же результатом, как исходный поток IIB.

Принципы:

- **Сравниваем поведение, а не текст.** «Идентичность XML» понимается как семантическая
  эквивалентность (граф шагов маршрута), а не посимвольное совпадение: форматирование, глубина
  вложенности и раскладка по файлам не важны.
- **Корпус в репозитории.** Каждая новая возможность конвертера обязана добавляться с fixture
  (тестовые артефакты IIB) + golden-файлы + e2e-набор данных.
- **Тесты не требуют установленного IIB/ACE.** Тестовые артефакты — обычные текстовые файлы.

## 2. Тестовый корпус (fixtures)

Репозиторий содержит корпус тестовых проектов IIB (`converter/src/test/resources/corpus/`),
эталонные результаты и e2e-данные:

```
converter/src/test/resources/corpus/
├── corr-01-simple-adapter/          # пример «несложный адаптер» (L1)
│   ├── Adapter.msgflow              # исходный поток
│   ├── Adapter.esql                 # логика Compute/Router
│   ├── expected/
│   │   ├── Adapter-route.xml        # golden: ожидаемый маршрут Camel (канонический)
│   │   └── e2e/
│   │       ├── dataset.yml          # входные сообщения + ожидаемые очереди/поля
│   │       └── messages/*.xml       # тестовые входные сообщения
├── corr-02-subflows/                # подпотоки, direct/inline + честные статусы (L2) — Should
├── corr-03-esql-mapping/            # ESQL-функции, CAST, IF/CASE (L2) — Should
└── corr-04-exotic/                  # редкие узлы/конструкции (L3) — Could
```

### Пример fixture: «несложный адаптер» ( уровня L1, Must)

Поток, который модифицирует сообщение и маршрутизирует его по ветвям:

```
MQInput(ADAPTER.IN) → Compute (копирует тело, ставит метку MQMD.ApplicationIdData)
                   → Route (`filterPattern: $Body/Adapter/Order/status='HIGH'`)
                       output: Match   → MQOutput(PRIORITY.Q)
                       output: Default → MQOutput(DEFAULT.Q)
                       catch/fail      → MQOutput(ERROR.Q)
```

В repo это сохраняется как настоящие файлы `.msgflow` (XML) и `.esql`, например:

```xml
<!-- Adapter.msgflow (фрагмент): формат — Eclipse EMF/XMI, как в реальных файлах IIB -->
<nodes xmi:type="ComIbmMQInput.msgnode:FCMComposite_1" xmi:id="Input"
       queueName="ADAPTER.IN" messageDomainProperty="XMLNSC"/>
<nodes xmi:type="ComIbmCompute.msgnode:FCMComposite_1" xmi:id="Enrich"
       computeExpression="esql://routine/adapter#Adapter_Compute1.Main"/>
<nodes xmi:type="ComIbmRoute.msgnode:FCMComposite_1" xmi:id="RouteByStatus">
  <filterTable filterPattern="$Body/Adapter/Order/status='HIGH'" routingOutputTerminal="Match"/>
</nodes>
```

```sql
-- Adapter_Compute1.esql (фрагмент)
CREATE COMPUTE MODULE Adapter_Compute1
  CREATE FUNCTION Main() RETURNS BOOLEAN
  BEGIN
    SET OutputRoot = InputRoot;
    SET OutputRoot.MQMD.ApplicationIdData = 'IIB-CAMEL-MIG';
    RETURN TRUE;
  END;
END MODULE;
```

## 3. Уровни тестирования

### 3.1. Уровень 1 — юнит-тесты компонентов конвертера (Must)

Тестируются внутренние единицы: парсеры, трансляторы, генераторы.

- **Парсер msgflow/subflow → IR (FR-1.4/1.5).** Разбор fixture → сравнение IR с ожидаемой моделью:
  количество узлов, терминалов, соединений, свойств (топология потока).
- **Парсер ESQL (FR-3.1).** Табличные тесты: пара «ESQL-фрагмент → ожидаемое AST/структура».
- **Транслятор выражений (FR-3.2).** Табличные тесты «выражение ESQL → ожидаемое simple/xpath»,
  включая таблицу соответствия функций (`CAST`, `SUBSTRING`, `CONCAT`, `UPPER`…).
- **Генераторы XML/Java/MapStruct.** Проверка выходных фрагментов на структуру и релевантность
  объявлений (короткие fixture → короткие фрагменты).
- **Инвентарь ESQL команды `analyze` (EsqlInventoryRenderer, 2026-10).** Табличные тесты вердиктов
  «как есть»: модуль в подмножестве → «переводимо полностью», модуль с ветвлением/функцией ≠ Main →
  «переводимо частично (N операторов переведено)», нет `Main`/FILTER → «вне подмножества»,
  ошибка разбора → честная строка плюс учёт в коде возврата; детерминизм (тот же вход →
  побайтово равный документ, D-3). CLI-контракт (`AnalyzeCommandTest`): `esql-inventory.md`
  рядом со схемами, esql-only каталог → код `0`, испорченный ESQL → код `2`.

### 3.2. Уровень 2 — golden-тесты: «XML преобразуется идентично» (Must)

Для каждой fixture конвертер генерирует артефакты, которые сравниваются с **golden-файлами** —
эталонами, хранящимися в корпусе.

**Как сравниваем (не «в лоб»):**

1. **Канонизация.** XML нормализуется (единое форматирование, сортировка атрибутов, устраняется
   мешающий «мусор» по позициям/координатам), только после этого текстовое сравнение.
2. **Граф маршрута.** Для чувствительных к порядку фрагментов строится граф: вершины — узлы DSL
   (`from`, `choice`, `when`, `bean`, `to`…), рёбра — порядок следования и ветвления,
   атрибуты — тип+аргументы. Сравнение графов — это и есть семантическая эквивалентность.
3. **Сравнение выражений.** Трансляция предикатов проверяется на поведенческом уровне: на наборе
   тестовых данных вычисляется и эталонный ESQL-предикат (мини-интерпретатор для основных функций),
   и сгенерированное `simple`-выражение — оба должны дать совпадающие результаты.

**Fail-режим и актуализация golden:**

- первое появление fixture — generation без golden: тест в статусе «golden не утверждён»;
- эталон утверждается явно (`--approve-golden` или флаг регенерации в Maven-профиле) и попадает
  в review: человек смотрит diff;
- далее любое **непреднамеренное** отклонение от golden — красный build;
- если изменение сознательное — в PR обновляется golden и снова проходит review.

### 3.3. Уровень 3 — e2e-тесты routing'а runtime-сервиса «маршрутизируется куда надо» (Should)

Цель: выполнить сгенерированный маршрут **в реальном runtime** и проверить поведение.

**Механика:**

- runtime запускается в тестовом контексте (`@CamelSpringBootTest`, camel-test-spring-junit5);
- вместо IBM MQ используется **встроенный брокер** (ActiveMQ Artemis): т.к. компонент `camel-jms`
  универсален, маршрут с MQInput/MQOutput работает и против Artemis — конфигурация маппится через
  настройки теста;
- сообщения отправляются во входную очередь компонентами теста; результаты забираются из выходных
  очередей.

**Декларативный dataset (описывается в `e2e/dataset.yml`, по датасету на corpus-директорию):**

```yaml
queues:                                     # каталог очередей корпуса (изоляция прогонов)
  - ADAPTER.IN
cases:
  - name: high-status-order-routed-to-priority-queue
    input:
      queue: ADAPTER.IN
      message: messages/order-high.xml
      mqmd:
        priority: 8
    expect:
      queue: ADAPTER.PRIORITY.Q                 # целевая очередь
      mqmd:
        priority: 8
        applicationIdData: IIB-CAMEL-MIG        # модификация Compute
  - name: regular-order-routed-to-default-queue
    input:  { queue: ADAPTER.IN, message: messages/order-low.xml }
    expect: { queue: ADAPTER.DEFAULT.Q }
  - name: malformed-message-goes-to-error-queue
    input:  { queue: ADAPTER.IN, message: messages/order-broken.xml }
    expect: { queue: ADAPTER.ERROR.Q }          # ветка catch/fail
```

Каждый кейс: отправить входное сообщение → дождаться/прочитать из ожидаемой очереди → сравнить
MQMD-поля и поля тела. Кейс **маршрутизируется** туда, куда надо = попадание в правильную очередь
с правильными модификациями и **отсутствие** сообщения в неправильных очередях.

E2e-тест параметризован по corpus-директориям (`E2eDatasetTest`, corr-01 и corr-02): corr-02
дополнительно проверяет сгенерированный из ESQL бин (`CheckCompute1`: JMS-свойство
`CommentField=CHECKED-BY-SUBFLOW`) и сохранение приоритета через direct:-подпоток.

**Дополнительные методы уровня 3:**

- **AdviceWith/mock-эндпоинты** (`camel mock:`) для сценариев, где брокер не нужен: быстро
  проверяем порядок шагов и результаты `bean`/`process` вызовов;
- **Тесты мапперов (FR-4).** Generated MapStruct-маппер: входной объект → ожидаемый выходной
  (объектное сравнение), тоже по декларативному dataset.

### 3.4. Дополнительно: приёмо-сдаточные сценарии (Could)

Отдельные e2e-сценарии «критичный поток», покрывающие собранный вариант развертывания
(jar + реальная конфигурация внешних соединений) — выполняются редко/по релизу.

## 4. CI и регрессия

| Триггер | Что гоняется | Время |
|---------|--------------|-------|
| Каждая ветка/PR (обязательный) | Л1 юнит + golden (corpus L1) | минуты |
| Nightly | Полный корпус (L2/L3) + e2e на встроенном брокере | десятки минут |
| По release | привитые сценарии (п. 3.4) + сборка заново корпуса | редкие |

Авто-проверки в CI:

- converter запускается над всем корпусом; отчёт о миграции не должен содержать статусов
  *не поддерживается* для **Must-узлов** базовой таблицы соответствия (FR-2.2), иначе build красный;
- класс ошибок «сгенерированные XML не загрузились в Camel» ловится e2e-обработкой (fail-fast, FR-R2.3).

## 5. Критерии завершённости фичи (Definition of Done)

Возможность конвертера считается готовой (по FR), когда:

1. в корпусе появилась фиксация (fixture), покрывающая эту возможность;
2. golden утверждён и проходит;
3. для «путевых» возможностей есть e2e-сценарий с dataset'ом (для Should-уровня);
4. отчёт о миграции строки fixture показывает ожидаемые статусы;
5. нет регрессий по остальному корпусу.

## 6. Приоритеты (MoSCoW)

| Приоритет | Элементы |
|-----------|----------|
| **Must** | корпус L1 («несложный адаптер»), юнит-тесты (парсер IR, таблицы трансляции), golden-тесты с семантическим сравнением (канонизация/граф), CI-проверка «нет не-поддерживаемых Must-узлов» |
| **Should** | корпус L2 (ESQL/подпотоки), e2e на встроенном брокере с dataset'ом, тесты мапперов, AdviceWith-моки |
| **Could** | корпус L3, автоутверждение golden с diff-ревью, дополнительные метрики (покрытие узлов), расширенные приёмо-сдаточные сценарии |
| **Won't** | полный эмулятор IIB/ESQL (мини-интерпретатор покрывает только ключевые функции), сравнение с реальным ACE-рантаймом в CI (возможно вручную, вне CI), property-based тестирование корпоративных символов |
