# Дизайн: рендерер диаграмм потоков (промежуточная модель → Mermaid)

> 🇬🇧 English version: [diagram-renderer-design.en.md](diagram-renderer-design.en.md)
>
> Функциональные требования: [functional-requirements.ru.md](functional-requirements.ru.md)
> Стратегия тестирования: [test-strategy.ru.md](test-strategy.ru.md)

## 1. Назначение и границы

Инструмент строит текстовые диаграммы Mermaid по потокам IIB (`.msgflow`, `.subflow`) и используется:

- при миграции — быстрая визуальная сверка «исходный поток ↔ сгенерированный маршрут»;
- при review — диаграммы хранятся в репозитории рядом с золотыми файлами корпуса (GitHub
  отрисовывает `.mmd` внутри Markdown автоматически);
- в документации — `docs/diagrams/*.mmd` либо блоки mermaid в README (встраиваются вручную по желанию).

**Что не входит в задачу:** редактирование потоков, интерактивный редактор (это FR-7.3, Could,
веб-интерфейс), рендеринг ESQL-логики внутри узлов, точная копия вида Toolkit (координаты, цвета
IBM). Речь о структурной диаграмме: узлы, типы, соединения, терминалы.

## 2. Ключевое архитектурное решение (D-1)

**Рендерер потребляет промежуточную модель (IR), а не сам разбирает `.msgflow`.**

Функциональные требования FR-1.4 вообще-то уже объектом требования ставят промежуточную модель,
содержащую топологию потоков. Дублировать парсер для отдельного «инструмента визуализации» —

1. дублирование кода и диагностики разбора (FR-1.3);
2. риск расхождения «две правды» о структуре потока: конвертер считает так, диаграмма рисует иначе;
3. lost-возможность: диаграмма — свободный smoke-тест корректности IR. Если рендерер рисует
   поток правильно, значит парсер вытащил топологию правильно, то есть и конвертер получил её.

Следствие: ответственность модуля — **только** «IR → Mermaid» и CLI-подводка. Реализация общего
парсера IR (и расширения IR под ESQL/схемы) — предмет основной конвертации (см. раздел 8 про
координацию).

## 3. Модель промежуточных данных (IR): минимальный срез топологии

> **Статус (после M1).** IR-модель реализуется параллельным треком основной конвертации
> (`converter.msgflow`: public-records `MsgFlow` / `FlowNode` / `FlowConnection`, парсер `MsgFlowParser`).
> Рендерер диаграмм потребляет её напрямую; сущности из эскиза ниже (`SourceRef`, `NodeCategory`)
> живут как внутренние детали рендера (`converter.diagram`). При расхождении контракта —
> правим здесь и согласуем с владельцем IR, не молча.

Пакет `com.example.iib_camel.converter.ir` (расширяемый позже ESQL/схемными типами). Эскиз:

```java
package com.example.iib_camel.converter.ir;

/** Поток или подпоток после разбора .msgflow/.subflow. */
public interface MsgFlow {
    String name();                       // имя файла без расширения
    SourceRef source();                  // источник: файл, позиция (FR-5.2, FR-1.3)
    List<FlowNode> nodes();              // узлы в порядке объявления (стабильный!)
    List<FlowConnection> connections();
    Set<SourceRef> unresolvedRefs();     // неразрешённые ссылки на .subflow (FR-1.5)
}

/** Узел потока. */
public interface FlowNode {
    String id();                         // id узла из файла (не нормализуем — трассировка)
    String name();                       // отображаемое имя
    String type();                       // тип узла IIB («MQInput», «Compute», …)
    NodeCategory category();             // категория для стилизации (см. таблицу ниже)
    Map<String, String> properties();    // распознанные свойства (очереди, хосты, ESQL-модуль…)
    boolean subflowRef();                // true для ссылки на подпоток
    Optional<SourceRef> subflowTarget(); // на что ссылается
}

/** Связь терминал → терминал. */
public interface FlowConnection {
    String sourceNodeId();
    String sourceTerminal();             // пустая строка, если в файле не указана
    String targetNodeId();
    String targetTerminal();
}

/** Ссылка на источник (файл + строка) для диагностики и отчёта. */
public interface SourceRef {
    Path file();                         // относительно корня входа
    int line();                          // 1-основная; -1 если неизвестна
}

/** Категория узла для раскраски диаграммы. */
public enum NodeCategory { INPUT, OUTPUT, PROCESS, ROUTE, ERROR, REFERENCE, OTHER }
```

Правила стабильности (важно для golden-тестов):

- **D-3:** `nodes()` — в порядке объявления в файле; внутренние идентификаторы зеркал диаграммы
  (`N1`, `N2`, …) присваиваются по этому порядку — и не зависят от имён узлов и хэш-кодов. Таким
  образом при переименовании узла diff-изменение диаграммы затрагивает только ярлык узла.
- **D-4:** ничего недетерминированного в рендере: нет системного времени, случайных id, итерации
  только по упорядоченным коллекциям.

## 4. Рендеринг Mermaid

### 4.1. Контракт вывода

```
flowchart LR                      // LR по умолчанию; TB — флаг --orientation TB
    N1["MQInput1"]:::input
    N2["Compute1"]:::process
    N3[["CheckStatus (subflow)"]]:::reference
    ...
    N1 --> N2
    N1 -. catch .-> N4             // рёбра не-основных терминалов — пунктиром с подписью
    ...
    classDef input fill:#e8eaf6,stroke:#3949ab,stroke-width:1px
    classDef output fill:#e8f5e9,stroke:#2e7d32,stroke-width:1px
    ...
```

Правила вывода:

- **D-5 (терминалы):** ребро подписывается и рисуется пунктиром, если исходный терминал неизвестен
  или не входит в список «основных выходов» источника. Сейчас основной выход — `out` (а для
  `Router` также `match*`). Список уточняется после реальных файлов (допущение A3) — это
  намеренно простое правило: точная семантика всех терминалов IIB не входит в задачу.
- **D-6 (ярлыки):** ярлык узла — имя узла; с новой строки (Mermaid `<br/>`) — тип узла. Дополнительные
  данные (например очередь для INPUT) пока не рисуем — «раскраску» откладываем до появления
  реальных файлов: важно знать, какие свойства действительно пишутся в файл (допущение A5).
- **D-7 (компоновка):** единый `flowchart`; при >30 узлах диаграмма остаётся одностраничной, но
 _Items_ раскладка может выродиться — флаг `--orientation TB` и последующее разделение по
  подграфам решаются после реальных файлов.

### 4.2. Регистр категорий узлов (стартовый, редактируемый)

| Категория | Узлы IIB (стартовый список) |
|-----------|------------------------------|
| INPUT | MQInput, HTTPInput, JMSInput, FileInput, SOAPInput, TCPInput, MQGet |
| OUTPUT | MQOutput, HTTPReply, JMSOutput, FileOutput, SOAPReply, TCPOutput, MQReply |
| ROUTE | Filter, Route, RouteToLabel, Label, Router |
| PROCESS | Compute, JavaCompute, Mapping, .NETCompute, Database, Collector, Aggregate, Resequence, Split, TimeoutControl, TimeoutNotify, SetVariable, ResetContentDescriptor, PASSTHRU, Trace |
| ERROR | Throw, TryCatch, ThrowError? |
| REFERENCE | ссылки на подпотоки (`.subflow`) |
| OTHER | любой неизвестный тип (фолбэк, стилизация с предупреждением) |

Реестр — обычный `Map<String, NodeCategory>` (ключ — `type()` как в файле, регистронезависимо),
фолбэк `OTHER`; пополняется по приходу реальных файлов. Никакой магии «отгадывания» нет.

### 4.3. Экранирование ([MermaidEscaper](../converter))

Замены в ярлыках (композируемо): `"` → `"`, `#` → `&num;`, `|` → `&#124;`, `<` → `<`,
`>` → `>`, переводы строк — пробелом. Идентификаторы зеркал (`N1`…) формируем сами, поэтому
экранировать их не нужно. Тест-таблица в юнит-тестах.

### 4.4. Дополнительные форматы вывода: AsciiDoc и Markdown-отчёт (D-8, пересмотрен 2026-10)

> **Статус:** исторический `--format ascii` («дерево-конспект») удалён — он дублировал
> то, что нагляднее показывает Mermaid, и засорял вывод. Класс `AsciiDiagramRenderer`
> и соответствующий вариант CLI исключены.

Второй формат `--format adoc` — документ AsciiDoc (`.adoc`): заголовок документа
(`= имя потока`, из имени IR), атрибут `:source-file:`, отсылка к графической схеме
(`.mmd` рядом) и таблицы узлов/связей. Назначение: документация пользователя
на Asciidoctor (`asciidoctor file.adoc`).

Третий формат `--format md` — инвентаризационный отчёт «как есть» (Markdown, `.md`,
рендерер `AnalysisMarkdownRenderer`): встроенный блок ```mermaid``` (GitHub/IDEA
рендерят), таблицы узлов (узел, тип, категория IIB, ключевое свойство, есть ли правило
конвертации — сверка с `RouteGenerator.SUPPORTED_BASE_KINDS`) и связей, а финальный
раздел «Готовность к миграции» отвечает на главный вопрос до миграции: предусмотрена ли
обработка всех узлов/сущностей IIB, и какие типы требуют ручной миграции (FR-2.7) или
расширения правил (FR-2.2, Should). Терминология отчёта — деловая: без внутренней
жаргонной лексики командным оформлениям («дерево-конспект», «золотник») в пользовательских
артефактах места нет.

Mermaid (`--format mermaid`) остаётся каноническим для GitHub; значения по умолчанию:
`--format all` — все три формата сразу. Требования детерминизма D-3/D-4 действуют для всех
форматов; HTML-просмотрщик — разовый артефакт обзора, не часть контракта.

## 5. CLI (команда `analyze`)

Каркас main-класса — picocli (единственная внешняя зависимость модуля на этот момент):

```
java -jar converter.jar analyze [--input <файл|каталог>] [--output <каталог>]
                                [--orientation LR|TB] [--format mermaid|adoc|md|all] [--fail-fast]
```

- `--input` — файл `.msgflow`/`.subflow`/`.esql` либо каталог (обход рекурсивно); по умолчанию
  `./input` относительно текущего каталога. FR-1.2 (пакетная обработка) соблюдена по построению.
- `--output` — выходной каталог, по умолчанию `./output` (создаётся при отсутствии);
  каждый артефакт → `<имя>.mmd`, `<имя>.adoc` либо `<имя>.md` (по `--format`, см. 4.4).
- `--format` — формат вывода: `all` (по умолчанию — все три), `mermaid`, `adoc` либо `md`
  (инвентаризационный отчёт, D-8).
- **ESQL-инвентарь** (2026-10): по `.esql`-файлам входа дополнительно строится системный
  `esql-inventory.md` — «как есть» по всему набору модулей: таблица (файл, модуль, тип,
  функций, операторов SET, конструкций вне подмножества) + вердикт переводимости по
  FR-3.2 (полностью / частично / вне подмножества; `Main` не найдена → вне). Артефакты
  конвертации (бины, модели) на этом этапе не создаются — граница с отчётом `convert`
  (FR-5.1) указана в самом документе. Единственный `.esql` как вход допускается — тогда
  схем нет, создаётся только инвентарь (код `0` при успешном разборе).
- Diagnostics (FR-1.3): `путь:строка: сообщение` на stderr; сводка на stdout
  (файлов, узлов, рёбер, предупреждений).
- **Коды возврата:** `0` — всё отрисовано; `1` — неверные аргументы; `2` — частичный успех
  (часть файлов не разобрана, остальные отрисованы); `3` — ни один файл не отрисован.

## 6. Требования к парсеру IR (контракт для разработчика парсера)

1. Namespace-агностичность (D-2): типы узлов и структура определяются по **локальным именам**
   элементов, а не по URI пространств имён — версии IIB меняют URI, суть формата стабильна.
2. Каждая сущность IR несёт `SourceRef(file, line)` — диагностика FR-1.3 начинается с парсера.
3. Ведомый "мягкий" режим: неизвестные узлы/атрибуты и структурные сюрпризы не прерывают разбор —
   складываются в warnings (FR-2.7-толкование, расширяемость FR-8.2).
4. Ссылки на `.subflow` ограничиваются записью в `unresolvedRefs` при отсутствии целевого файла
   во входном наборе — рендерер рисует узел-заглушку.

## 7. Тестирование (в связке с [тестовой стратегией](test-strategy.ru.md))

- **Юнит-уровень:** экранирование (таблица замен); рендерер на синтетической IR — ярлыки, рёбра,
  подписи терминалов, порядок classDef, категоризация по реестру.
- **Golden-уровень:** для каждой фиксации корпуса (`converter/src/test/resources/corpus/corr-0X-*`)
  рендерер строит `Expected`-файлы `expected/<имя потока>.mmd` рядом с золотыми маршрутами.
  Процесс утверждение goldens — как в стратегии: первое появление — «golden не утверждён»,
  подтверждение явным флагом регенерации, далее любое непреднамеренное отклонение — красный build.
- **Детерминизм:** тот же вход дважды → побайтно равный вывод (юнит-тест).
- **Assumption-audit:** список допущений A1–A8 из раздела 8 ведёт осмысленные статусы; после
  прихода реальных файлов от сопутствующей сессии — прогон, проставление статусов, правки модели
  категорий и правила терминалов.

## 8. Допущения о формате (A1–A8) — что проверяем на реальных файлах

Соседняя сессия добавляет реальные `.msgflow`/`.subflow` (соглашение о месте и контексте — см. 8.1).
Пока файлы не пришли, парсер построен на общих знаниях о формате; каждое допущение нужно снять
фактами из реальных файлов, чтобы «докрутить» парсер/рендерер ровно там, где надо:

| № | Допущение | Как проверим | Риск |
|---|-----------|--------------|------|
| A1 | Корень файла — элемент потока (`flow`-family), namespace варьируется между версиями MB/IIB/ACE | посмотреть корень и ns-URI реальных файлов; парсер namespace-агностичен — риск низкий | низкий |
| A2 | Узлы лежат в выделенном контейнере (`nodes`-family); тип узла — по имени элемента либо атрибуту `type` | структура контейнера на реальном файле | средний |
| A3 | Соединения — плоский список элементов `connections` с атрибутами сторона/терминал (source/target) | точные имена атрибутов терминалов | средний |
| A4 | Подпоток: свой файл; ссылка в родителе — узел с указанием на `.subflow` | формат файла `.subflow`, вид узла-ссылки | **снят (corr-02)**: узел-ссылка — `xmi:type="Имя.subflow:FCMComposite_1"` (+ xmlns-декларация), ввод/вывод — `eflow:FCMSource`/`eflow:FCMSink` (канон `ot4i/ace-bob`) |
| A5 | Свойства узлов — подэлементы/атрибуты (очередь INPUT, хост MQ, ESQL-модуль); какие реально заполнены | посмотреть, какие свойства стоит показывать под ярлыком | низкий |
| A6 | Файл содержит служебные координаты Toolkit (раскладка узлов) | убедиться, что их игнорирование безопасно | низкий |
| A7 | Различия версий (MB9 / IIB10 / ACE11+) — в ns-URI и мелких полях; кодировка UTF-8 (возможен BOM) | сверить файлы разных версий, если есть | низкий |
| A8 | Встречаются нестандартные/пользовательские типы узлов | фолбэк OTHER + предупреждение покрывает | низкий |

### 8.1. Соглашение о месте fixtures от соседней сессии

Файлы кладутся в корпус согласно [тестовой стратегии](test-strategy.ru.md):
`converter/src/test/resources/corpus/corr-0X-<название>/<ИмяПотока>.msgflow` (+ `.esql`, `.subflow`
рядом). Это позволяет сразу прикладывать goldens в `expected/` и запускать assumption-audit одной
командой. В дополнение к файлам желательно однострочное сопровождение: версия IIB/ACE, были ли
подпотоки, выхолощены ли имена (см. рис. R-2).

## 10. Риски

| Риск | Смягчение |
|------|-----------|
| R-1: читаемость Mermaid на потоках 30+ узлов | `--orientation TB`; в перспективе — разбиение карт по входным узлам (после реальных файлов, D-7) |
| R-2: конфиденциальность бизнес-имён в корпусе и диаграммах | fixtures в репозитории — выхолощенные копии; диаграммы строятся из corpus, а не из боевых файлов |
| R-3: расхождение с парсером основной конвертации при параллельной разработке | D-1: парсер один, рендерер потребляет IR; дополнения IR — новые типы, а не ломка контрактов |
| R-4: версии Mermaid (GitHub/mermaid-cli) по-разному рендерят экзотические конструкции | используются только базовые возможности `flowchart`; проверка на GitHub и mmdc в M3 |
