# Анализ IIB для планирования ручной миграции

Дата: 26 октября 2026 года. Статус: предложение по развитию `analyze`, а не описание реализованных возможностей.

Цель: по каталогу `.msgflow`, `.subflow`, `.esql` получить карту транспортов, потоков, зависимостей и участков ручной
работы. Полный перевод ESQL не является условием получения полезного отчёта. Конвертер и самостоятельный runtime
сохраняют свои задачи; runtime не должен зависеть от модели анализатора.

Документ содержит только общие требования и синтетические обозначения. Исходники пользователя, их имена, результаты
предметного анализа и ручные уточнения хранятся локально в `.private/` или вне репозитория.

Первый структурный выпуск реализован 26 октября: `analyze --inventory`. В нём доступны роли MQ/Kafka, продвинутые
свойства экземпляров подпотоков, каталог назначений, карта связей и исходные позиции. ESQL не читается. Подробные
границы выпуска — [пример и руководство](../examples/analyze/inventory/README.ru.md), результаты проверки —
[ход реализации](implementation-progress.ru.md). Остальные разделы описывают общий план, включая будущие возможности.

## Что уже есть

Проверены код и запуск `analyze` на публичном синтетическом наборе `examples/analyze/system`:

- `MsgFlowParser` извлекает узлы, свойства, соединения, терминалы и ссылки на подпотоки.
- Mermaid и Markdown показывают отдельные потоки; таблица узлов выводит `queueName` и ссылку Compute на ESQL.
- `ProjectValidation` использует генератор маршрутов и переводчик ESQL для оценки готовности к конвертации.
- ESQL-инвентарь показывает модули и соответствие поддержанному подмножеству переводчика.

Пока отсутствуют отдельный каталог транспортных точек, общая карта обмена между потоками, разрешение promoted
properties для каждого экземпляра подпотока и независимая оценка полноты анализа. Сложный ESQL может не пройти
текущий парсер целиком. Категория отображения узла, например INPUT для MQGet, недостаточна для определения его роли.

## Результат для пользователя

После одного запуска предлагаются следующие связанные представления:

| Представление | На какой вопрос отвечает |
| --- | --- |
| Сводка проекта | Какие файлы прочитаны, какие зависимости отсутствуют, где анализ неполон? |
| Каталог очередей и топиков | Кто читает и пишет, в каком контексте брокера, откуда получено имя? |
| Обзор обмена | Какие потоки потенциально связаны общей очередью или топиком? |
| Карточка потока | Где его входы, возможные выходы, ветки ошибок, подпотоки, ESQL и обращения к БД? |
| План ручного переноса | Какие обработчики и общие компоненты написать, что уточнить и как проверить? |

Основной результат — Markdown с Mermaid. CSV подходит для каталога очередей/топиков, версионированный JSON — для
дальнейших инструментов и проверки изменений. HTML-просмотрщик с поиском можно добавить после стабилизации модели.

Общая схема показывает поток целиком как один блок. Подробная схема раскрывается отдельно, с сохранением границ
подпотоков. Не требуется строить одну гигантскую диаграмму или перечислять все комбинации маршрутов в графе.

## Достоверность и границы выводов

Для каждого найденного значения сохраняются файл, узел или процедура, диапазон исходного текста и способ получения:

| Способ получения | Значение для пользователя |
| --- | --- |
| Задано в файле | Значение явно записано в свойстве узла или литерале ESQL |
| Разрешено статически | Значение получено через свойства экземпляра подпотока или поддержанное выражение; показана цепочка |
| Подтверждено вручную | Значение внесено человеком, сохранены основание и привязка к версии исходника |
| Не определено | Известна операция чтения/отправки, но адрес зависит от сообщения, БД или отсутствующей конфигурации |

Наличие значения в исходнике не доказывает его использование в развёрнутой системе. Конфигурация развёртывания и
политики могут его изменить. Без этих файлов отчёт явно описывает исходный проект, а не фактическую production-среду.

Полнота оценивается отдельно для топологии, адресов, разрешения зависимостей и управления выходами. Число найденных
очередей не выдаётся за процент покрытия. Нераспознанный участок, неоднозначная ссылка и динамический адрес остаются
видимыми в отчёте; отсутствие находок не означает отсутствие взаимодействий.

## Транспортные точки и подпотоки

Нужен реестр правил анализа типов узлов, независимый от списка поддержанной генерации Camel. Неизвестный тип
сохраняется в графе вместе со свойствами и отметкой о неизвестных эффектах.

Роли задаются для использования очереди конкретным узлом, а не навсегда для самой очереди:

- MQInput и KafkaConsumer — точки поступления сообщений в поток.
- MQOutput и KafkaProducer — отправки из потока; после узла отправки выполнение может продолжаться.
- MQGet — дополнительное чтение внутри уже выполняющегося потока, а не отдельный входной consumer.
- MQReply и режим Reply To Queue — отправки, адрес которых может прийти из заголовков сообщения.
- Input/Output подпотока — его интерфейсные терминалы, а не очереди брокера.

MQOutput может брать назначение из свойства, reply-заголовка или списка в LocalEnvironment. Режим назначения должен
участвовать в интерпретации имени: наличие `queueName` само по себе не доказывает, что именно туда идёт отправка.
Это соответствует [описанию MQOutput в IBM](https://www.ibm.com/docs/en/app-connect/12.0.x?topic=nodes-mqoutput-node).
Роль MQGet как чтения внутри потока описана в
[документации request-узлов IBM](https://www.ibm.com/docs/en/integration-bus/9.0.0?topic=use-request-nodes).

Подпотоки анализируются в контексте каждого вызова: определение, значения по умолчанию, promoted properties,
`attributeLinks`, переопределения экземпляра, входные/выходные терминалы. Два экземпляра одного подпотока могут
использовать разные очереди. Отсутствующее определение, цикл ссылок или неоднозначное имя не подменяются первым
найденным файлом. Сохраняются полное имя и путь, а не только имя файла без каталога.

Межпоточная связь строится по транспорту, контексту брокера и точному имени назначения. Для MQ учитывается queue
manager, для Kafka — контекст кластера и топик. Совпадение только строки имени даёт кандидата связи. При нескольких
читателях показываются все кандидаты, без обещания доставки каждому. Алиасы MQ и внешние потребители требуют
дополнительной конфигурации или ручного подтверждения.

## Минимальный анализ ESQL

Выделить общий лексический разбор с позициями из существующего парсера и добавить отдельный анализатор фактов.
Переводчик сохраняет строгие ограничения. Анализатор должен продолжать извлечение после неподдержанного оператора,
отмечая неполные участки; при повреждённом тексте он не должен придумывать недостающую структуру.

На первом этапе извлекаются:

- модули, процедуры, функции, BROKER SCHEMA, PATH и ссылки из Compute/Filter/Database;
- `PROPAGATE`, его терминал или label, `RETURN`, `THROW`, обработчики исключений;
- `CALL` и вызовы пользовательских функций внутри выражений, включая неразрешённые зависимости;
- записи в транспортные назначения LocalEnvironment и reply-поля;
- признаки работы с внешней БД, datasource, статически видимые объекты и динамический SQL.

SQL-подобное выражение над деревом сообщения не считается обращением к БД только из-за слова SELECT. Строка,
похожая на очередь, также не становится назначением без соответствующего контекста использования.

Сначала фиксируются факты и выражения. Затем можно ограниченно вычислять литералы, константы и простую конкатенацию.
После неизвестного вызова, изменения через REFERENCE или неподдержанного ветвления затронутые значения становятся
неизвестными. Условные отправки остаются возможными; число повторов в цикле не угадывается. Учёт Compute Mode и
передачи LocalEnvironment необходим прежде, чем связывать присваивание с фактическим downstream-назначением.

`PROPAGATE` выполняет downstream-ветку синхронно, после успешного возврата ESQL может продолжаться. Для Compute
`RETURN TRUE` допускает последующую автоматическую отправку через `out`, а `RETURN FALSE` подавляет её; у Filter
значение RETURN выбирает другой терминал. Поэтому простой список соединений не описывает все условия выполнения.
Семантика: [PROPAGATE](https://www.ibm.com/docs/en/integration-bus/10.0.0?topic=statements-propagate-statement),
[RETURN](https://www.ibm.com/docs/en/app-connect/13.0.x?topic=statements-return-statement).

## Ручные уточнения и подзадачи переноса

Предусмотреть локальный YAML с дополнениями к результату: неизвестный broker alias, возможные динамические
назначения, смысл нестандартного узла, выбранный целевой модуль runtime, ссылки на ручное описание обработчика.
Найденные автоматически факты сохраняются отдельно; уточнение содержит обоснование и не скрывает противоречия.
Привязка включает путь, идентификатор узла/экземпляра и отпечаток исходника. После изменения исходника дополнение
помечается требующим проверки. Повторная генерация не перезаписывает ручные материалы.

Для необычных типов узлов возможны небольшие Java-правила анализа с общим контрактом: распознанные операции,
назначения, исходные позиции и ограничения. Первые типовые правила лучше включить непосредственно в анализатор;
универсальный загрузчик плагинов и собственный движок исполнения сейчас не нужны.

Карточка ручной подзадачи содержит входной контракт, преобразование, обращения к БД, выходы и их условия, ошибки,
границы транзакции, неизвестные места и критерии проверки. Примеры подзадач: разобрать один Compute; перенести общую
процедуру чтения справочника; реализовать обработчик Java; проверить ветку ошибок; сравнить выходные сообщения.
Общий helper учитывается как зависимость нескольких потоков, чтобы не переносить его заново в каждом модуле.

План может предлагать соответствие `поток IIB → модуль runtime`, но решение подтверждается вручную. Синхронная ветка
PROPAGATE с продолжением обработки и асинхронная отправка из outbox не считаются автоматически эквивалентными.
Смена транспорта, ACK, транзакции, кодировка и заголовки входят в отдельные проверки переноса.

## Очерёдность реализации

| Пакет | Содержание | Критерий завершения |
| --- | --- | --- |
| A1. Модель анализа | ProjectAnalysis, SourceRef, факты, неизвестные участки, реестр ролей; независимость от генератора | Сложный или отсутствующий ESQL не скрывает доступную топологию; строгая конвертация не ослаблена |
| A2. Каталог и подпотоки | MQ/Kafka, свойства назначения, resolver, promoted properties по экземплярам, Markdown/CSV | Показаны статические входы/выходы и неизвестные назначения; два вызова подпотока корректно различаются |
| A3. Факты ESQL | Терминалы, RETURN, вызовы, БД, динамические адреса с позициями | Существенные находки извлекаются и из непереводимого ESQL; неизвестные области явно отмечены |
| A4. Карта системы | Связи через назначения, обычные/ошибочные пути, агрегированный Mermaid, JSON | Нет ложного объединения одинаковых очередей разных брокеров; кандидат связи отличим от разрешённой связи |
| A5. Рабочие материалы | Ручные YAML-уточнения, карточки модулей, зависимостей и задач переноса | Повторный анализ сохраняет дополнения и выявляет их устаревание |

Рекомендуемый первый полезный выпуск — A1 + A2 и простой обзор очередей и использующих их потоков из A4.
Он полезен без перевода ESQL: неизвестные динамические части будут обозначены явно. После согласования общей модели
разбор подпотоков, ESQL-сканер и отчёты можно вести независимыми подзадачами; интеграцию и ревью проводить совместно.
Автоматическое переписывание сложного ESQL, полное доказательство достижимости ветвей и UI отложены.

## Проверка результата

Использовать новые синтетические примеры: несколько входов, продолжение после отправки, MQGet внутри потока,
ветки catch/failure, неподключённые узлы, многовыходные и отсутствующие подпотоки, promoted properties двух
экземпляров, одинаковые имена файлов в разных каталогах и очереди в разных broker-контекстах.

Для ESQL проверить ложные ключевые слова в комментариях/строках, вызовы в выражениях и вспомогательных процедурах,
динамические терминалы/очереди, ранние RETURN, циклы, усечённый последний модуль при сохранении ранее найденных
фактов, корректные исходные позиции и явную неполноту результатов. Пустой файл не выдаётся за полный анализ модуля.

Отчёты должны быть детерминированы, безопасно экранировать исходные подписи и показывать отсутствие внешних
конфигураций. Нужны CLI-проверки на свежем результате и регрессии существующей строгой конвертации.
