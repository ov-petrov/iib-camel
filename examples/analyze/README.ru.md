# Ручная проверка `analyze`

Небольшие входы для знакомства с инвентаризацией. Это учебные примеры формата XMI/ESQL, а не представительный корпус IBM и не утверждение о полной поддержке форматов IIB/ACE.

## Состав набора

- `system/OrderIntake.msgflow` — MQInput → Compute → Route с двумя строками `filterTable`, режимом `First`, тремя ветвями (в том числе подпоток) и отдельным `Input.catch`.
- `system/Audit.subflow` — подпоток Input → Trace → Output. Trace распознаётся и показывается в схеме; в таблице покрытия его тип помечается «нет (ручная миграция)».
- `system/OrderModules.esql` — три модуля: безусловные SET как полностью переводимое подмножество, IF с SET как частичный случай, и CALL вне базового подмножества.
- `negative/` — некорректный XML, повторяющийся `xmi:id`, ссылка связи на отсутствующий узел и некорректный ESQL.
- `semantic-limits/UnvalidatedGraph.msgflow` — XML корректен, но в графе есть цикл, Compute-ссылка на отсутствующий ESQL-модуль и ссылка на отсутствующий подпоток. `analyze` разбирает и рисует такой граф; команда **не проверяет циклы и разрешение этих ссылок**.

Все XML-примеры используют объявленные XMI, Ecore, eflow и типовые namespace. Они намеренно небольшие и не заменяют экспорт из целевой версии IBM Integration Bus / App Connect Enterprise.

## Подготовка

Нужен JDK 25 и Maven. Из корня проекта соберите проект:

```sh
mvn -B verify
```

Ниже команды запускаются из корня репозитория. Результаты пишутся в игнорируемый `target/manual-analysis/`.

## Основной запуск

Сгенерировать Mermaid, AsciiDoc, Markdown-отчёты и инвентарь ESQL для всех корректных демонстрационных входов можно так:

```sh
java -jar converter/target/converter.jar analyze \
  --input examples/analyze/system \
  --output target/manual-analysis/system-lr \
  --format all --orientation LR
```

Ожидается exit code **0**: два потока, 6 диаграммных артефактов, 10 узлов, 8 связей и 3 ESQL-модуля (по одному полному, частичному и вне подмножества). Для отдельного анализа подпотока укажите `--input examples/analyze/system/Audit.subflow`; результат не доказывает, что он разрешён из родительского проекта.

Начните просмотр с `target/manual-analysis/system-lr/OrderIntake.md`, затем откройте `Audit.md` и `esql-inventory.md`. Markdown содержит схему, таблицы узлов и терминалов, оценку покрытия типов. Откройте его в просмотрщике с поддержкой Mermaid. Отчёт пока не выводит все свойства узла, например строки `filterTable`, и не объединяет схемы родителя и подпотока.

Поддерживаемые значения `--format`: `mermaid` или `.mmd`, `adoc` или `.adoc`, `md` или `.md`, `all`. `all` создаёт диаграмму каждого из трёх форматов. Когда во входе есть ESQL, `esql-inventory.md` создаётся дополнительно независимо от выбранного формата диаграммы. `--orientation LR` задаёт направление слева направо, `--orientation TB` — сверху вниз; параметр применяется к Mermaid и Markdown со встроенной Mermaid-схемой.

Чтобы получить только Markdown-диаграмму в направлении сверху вниз:

```sh
java -jar converter/target/converter.jar analyze \
  --input examples/analyze/system/OrderIntake.msgflow \
  --output target/manual-analysis/order-tb \
  --format .md --orientation TB
```

Ожидается **0**. Для проверки AsciiDoc поменяйте формат на `adoc`; для отдельного Mermaid-файла — на `mermaid`.

## ESQL и ошибки входов

Одиночный ESQL-файл является допустимым входом:

```sh
java -jar converter/target/converter.jar analyze \
  --input examples/analyze/system/OrderModules.esql \
  --output target/manual-analysis/esql \
  --format md
```

Ожидается **0** и `esql-inventory.md`: 3 модуля — 1 полностью переводимый, 1 частично переводимый и 1 вне подмножества. Оценка относится к текущему ограниченному подмножеству ESQL. Частичный статус означает, что распознана лишь часть операций; generated-бин такого модуля при `convert` остановится до их исполнения. Пооператорная детализация находится в отчёте `convert`, а не `analyze`.

Обработать папку с негативными примерами, продолжая после ошибок:

```sh
java -jar converter/target/converter.jar analyze \
  --input examples/analyze/negative \
  --output target/manual-analysis/negative \
  --format all
```

Ожидается **2**: опубликован `esql-inventory.md` с ошибкой ESQL; ошибки потоков перечислены в stderr. Пакетный режим продолжает обработку остальных входов. Для остановки после первой ошибки добавьте `--fail-fast`; для этой папки ожидается **3**, так как первый файл по порядку не проходит разбор и до первой успешной диаграммы дело не доходит.

В смешанном каталоге примеров тоже есть ошибки, поэтому ожидается **2**:

```sh
java -jar converter/target/converter.jar analyze \
  --input examples/analyze \
  --output target/manual-analysis/mixed \
  --format all
```

В текущем наборе фактически успешно разбираются 3 из 6 файлов потоков, создаются 9 диаграммных файлов, обрабатываются 2 ESQL-файла с 3 найденными модулями; учтено 4 ошибки. С тем же входом и `--fail-fast` ожидается **3**: первым по порядку встречается повреждённая связь, и успешных результатов до неё нет.

Текущий счётчик ESQL «вне подмножества» включает также файлы с ошибкой разбора: для смешанного набора он равен 2, хотя разобранный модуль вне подмножества только один. Ошибочный файл выделен отдельной строкой инвентаря; это ограничение текущей сводки.

Коды команды: **0** — ошибок обработки нет; **1** — неправильные аргументы, отсутствующий вход или неподдерживаемое расширение одиночного файла; **2** — ошибки разбора при наличии успешной схемы или ESQL-инвентаря; **3** — нет подходящих входов, все потоки не разобраны и нет ESQL-инвентаря либо заблокирована публикация. Даже инвентарь с единственным ошибочным ESQL считается опубликованным результатом и даёт **2**. Это коды CLI, а не уровни готовности миграции.

## Границы семантической проверки

```sh
java -jar converter/target/converter.jar analyze \
  --input examples/analyze/semantic-limits \
  --output target/manual-analysis/semantic-limits --format all
```

Ожидается **0**: 1 поток, 4 узла, 4 связи. В отчёте все типы входят в базовый набор, хотя граф содержит цикл и отсутствующие зависимости. Раздел «Готовность к миграции» сейчас проверяет только покрытие типов узлов. Проверки графа и разрешение ссылок команды `convert` здесь не запускаются; зелёная оценка типов не подтверждает готовность всего потока.

## Существующий тестовый корпус

```sh
java -jar converter/target/converter.jar analyze \
  --input converter/src/test/resources/corpus \
  --output target/manual-analysis/corpus --format all
```

Ожидается **0**: 4 потока, 12 диаграммных артефактов, 18 узлов, 14 связей; 3 ESQL-модуля — 2 полных и 1 частичный. Для просмотра есть `Adapter.md`, `Order.md`, `Check.md`, `Adjust.md` и `esql-inventory.md`. Исходники корпуса также используются тестами свежей генерации и runtime; в `corr-01-simple-adapter/expected/e2e/` есть XML-сообщения для сценариев HIGH/LOW/повреждённый XML.

## Выходные файлы и границы результата

В каталоге результата `.iib-camel-analyze.tsv` — manifest опубликованных файлов с SHA-256. При следующем запуске конвертер сверяет принадлежащие ему результаты. Если файл был вручную изменён, он откажется его перезаписывать; выберите новый пустой каталог вывода или восстановите файл из результата генерации.

Смена `--format all` на `--format md` в том же каталоге удаляет прежние неизменённые `.mmd`/`.adoc`, поскольку они больше не входят в результат. Посторонние файлы сохраняются. Если имя потока повторяется, `analyze` добавляет суффиксы `-2`, `-3` и предупреждает в stderr; это не разрешает неоднозначность ссылок проекта.

Проверка защиты от перезаписи:

```sh
java -jar converter/target/converter.jar analyze \
  --input examples/analyze/system/OrderIntake.msgflow \
  --output target/manual-analysis/overwrite-check --format md
printf '\nmanual edit\n' >> target/manual-analysis/overwrite-check/OrderIntake.md
java -jar converter/target/converter.jar analyze \
  --input examples/analyze/system/OrderIntake.msgflow \
  --output target/manual-analysis/overwrite-check --format md
```

Первый запуск возвращает **0**, второй — **3** и сообщает, что файл вручную изменён или не принадлежит текущей генерации.

Успешный exit code означает, что эта команда смогла разобрать указанные файлы и записать инвентаризацию. Он не подтверждает полноту знания IBM-форматов, корректность бизнес-семантики, отсутствие циклов, наличие зависимостей, готовность к конвертации или готовность к production-миграции. Для этого нужны отдельные проверки на целевой версии IIB/ACE и на реальном проекте.
