# Инвентаризация очередей и топиков

Нейтральный синтетический проект для режима `analyze --inventory`. Все файлы созданы для тестирования инструмента.

```sh
mvn -B -f converter/pom.xml package
java -jar converter/target/converter.jar analyze --inventory \
  --input examples/analyze/inventory --output output/inventory
```

Начните с `output/inventory/system-overview.md`. Рядом находятся каталог `endpoints.csv`, структурированный
`project-inventory.json` версии 1 и отдельные карточки `flow-*.md` со ссылками из общей страницы.

В примере четыре корневых потока и одно определение подпотока. `Publisher.msgflow` дважды вызывает
`Publisher.subflow` с разными значениями продвинутого свойства `targetQueue`. `Consumer.msgflow` читает одну из
выходных очередей и использует MQGet внутри обработки. `OtherBroker.msgflow` содержит такое же имя очереди на другом
queue manager и не объединяется с ней. `Events.msgflow` показывает Kafka consumer/producer.
В учебном Kafka-потоке одинаковый топик задан на входе и выходе: обзор показывает возможную петлю обмена.

Ссылки на ESQL сохраняются как непрозрачные обработчики. Содержимое `.esql` в этом режиме не читается; обнаруженные
имена файлов перечисляются как пропущенные. Обычный режим `analyze` доступен отдельно.

Роли относятся к использованию конкретным узлом: CONSUME — вход, PRODUCE — отправка, FETCH — дополнительное чтение,
REPLY — ответ с потенциально динамическим назначением. Отдельно показаны шаблоны подпотоков и их экземпляры.
DECLARED означает значение из файла, RESOLVED — разрешение через параметры подпотока, UNKNOWN — недостаток данных.
CONFIGURED у связи означает совпадение статического назначения и контекста брокера; CANDIDATE требует уточнения.
Структурный путь не подтверждает фактическое выполнение и условия отправки.

Пока поддержаны MQInput, MQOutput, MQGet, MQReply, KafkaConsumer и KafkaProducer. MQOutput без явного destinationMode
использует статическое queueName; подтверждённый режим `list` остаётся динамическим. Остальные явные режимы
консервативно помечаются UNKNOWN. Политики подключения, CCDT, алиасы брокера и настройки развёртывания не разрешаются.
JMS, REST/SOAP и анализ бизнес-логики ESQL в эту итерацию не входят. XML с ошибками разбирается на уровне отдельных
файлов; корректные файлы сохраняются в частичном отчёте. Защита от внешних XML-сущностей сохранена.

Коды выхода: 0 — отчёт опубликован; 1 — неверные аргументы; 2 — частичный результат с ошибками либо предупреждения
при `--strict`; 3 — нет разобранных потоков или публикация заблокирована. `--fail-fast` останавливает чтение после
первой ошибки файла. `--inventory` всегда создаёт Markdown, CSV и JSON; `--format` относится к обычному `analyze`.

Для рабочих исходников и отчётов используйте `.private/` или каталог вне репозитория. Исходные файлы не меняются.
Сгенерированные файлы защищены от перезаписи ручных правок; при повторном запуске изменённый отчёт нужно сохранить
отдельно или выбрать новый каталог вывода.
