# Транзакции и доставка

`InboxService.accept` открывает собственную транзакцию PostgreSQL. Она фиксирует идентичность входа, изменения бизнес-таблиц через тот же `DataSource` и неизменяемые выходные сообщения. Метод возвращается после коммита. Повтор с тем же ключом `(moduleId, source, messageId)` не запускает обработчик повторно; другое тело при том же ключе вызывает конфликт. Не меняйте назначение `source` между перезапусками.

JMS-потребитель завершает свою локальную транзакцию после успешного возврата маршрута. Если процесс упадёт после коммита БД до подтверждения JMS, повтор отсеет inbox. Kafka-потребитель с `autoCommitEnable=false`, `allowManualCommit=true`, `breakOnFirstError=true` подтверждает offset только после успешного `accept` на потоке потребителя. Ошибку нельзя скрывать и нельзя коммитить более поздний offset той же partition, пропуская неуспешный.

Планировщик выбирает ограниченный набор строк с `FOR UPDATE SKIP LOCKED`. Состояния:

| Статус | Значение |
| --- | --- |
| READY | Доступно для отправки после `available_at` |
| IN_PROGRESS | Захвачено токеном и временной арендой `lease_until` |
| PROCESSED | Брокер подтвердил отправку, затем PostgreSQL сохранил результат |
| FAILED | Исчерпано настроенное число попыток; требуется разбор оператором |

Брокер вызывается без открытой транзакции БД. Для JMS отправитель ждёт коммита persistent-сообщения, для Kafka — результата отправки с `acks=all`. Затем отдельная транзакция помечает строку `PROCESSED`, проверяя токен владельца. После падения процесса истёкшая аренда позволяет повторный захват. Токен защищает статус от перезаписи старым отправителем, но не отменяет уже выполняющуюся отправку.

Сбой после принятия брокером и до записи `PROCESSED` допускает дубликат. UUID исходящего события сохраняется в заголовке `applicationEventId`; принимающая сторона должна дедуплицировать его. `PROCESSED` не означает, что конечный бизнес-потребитель обработал сообщение. XA между PostgreSQL и брокерами нет. Глобальный порядок между отправителями и разными брокерами не гарантируется.

Выбирайте `lease` больше предельного времени последовательной отправки всего пакета, либо уменьшайте `batch-size`: слишком короткая аренда повышает число повторов. Число попыток, экспоненциальная задержка и срок хранения inbox/outbox должны соответствовать требованиям конкретного модуля. Автоматической очистки и административного повторного запуска `FAILED` пока нет. Не удаляйте inbox, пока возможна повторная доставка исходного сообщения.

Проверки реальной БД включаются переменными `IIB_TEST_POSTGRES_URL`, `IIB_TEST_POSTGRES_USER`, `IIB_TEST_POSTGRES_PASSWORD`. Они создают и удаляют только собственные случайные схемы. Реальные проверки брокеров используют `IIB_TEST_ARTEMIS_URL`, `IIB_TEST_ARTEMIS_USERNAME`, `IIB_TEST_ARTEMIS_PASSWORD`, `IIB_TEST_KAFKA_BOOTSTRAP_SERVERS`. Для обычного `mvn verify` без этих переменных внешние проверки пропускаются.
